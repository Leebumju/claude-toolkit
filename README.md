# claude-toolkit

Claude Code 스킬 모음. **필요한 것만 골라서 켠다.**

각 플러그인은 독립이라 하나만 켜도 되고 전부 켜도 된다.

## 설치

```sh
/plugin marketplace add Leebumju/claude-toolkit
/plugin install ios-measure@bumju-toolkit
```

목록에서 고르려면 `/plugin` 만 쳐도 된다.

## 무엇이 있나

| 플러그인 | 쓰는 때 | 범용 |
|---|---|---|
| `ios-modernize` | 레거시를 신규 패턴으로 옮길 때. 모듈 경계를 세울 때 | iOS 프로젝트 전부 |
| `ios-measure` | 앱이 느릴 때. 원인을 추측하지 않고 재려 할 때 | iOS 프로젝트 전부 |
| `code-lens` | 코드베이스에서 개선점 목록만 뽑을 때 | 언어 무관 |
| `skill-forge` | 만든 스킬에 무엇이 빠졌는지 볼 때 | 스킬을 쓰는 누구나 |
| `hiring-assignment` | 채용 과제를 받았을 때 | 과제 전형 한정 |

앞으로 만들 스킬과 그 근거는 [`ROADMAP.md`](ROADMAP.md) 에 있다.

### `ios-modernize`

레거시 iOS 코드를 신규 패턴으로 옮기는 절차 둘.

| 스킬 | 하는 일 |
|---|---|
| `legacy-port` | 화면 하나를 옮기고 **동작이 안 바뀐 것을 증명한다** |
| `modularize-ios` | 한 타깃을 계층·피처 모듈로 가른다 |

**`legacy-port` 의 핵심은 옮기는 단계가 아니라 그 앞이다.** 코드를 한 줄도 고치기 전에
현재 동작을 파일로 적는다. 안 적으면 "동작을 보존했다" 는 주장 자체가 불가능하다.
옮긴 뒤에는 그 기록과 항목별로 대조한다 — 분기 · 호출 순서 · 타이밍 · 에러 처리 ·
표시 문자열 · 취소 · 스레드.

**`modularize-ios` 의 끝은 파일을 옮기는 것이 아니다.** 위반 `import` 를 넣어
빌드가 죽는 것을 확인하는 것까지다. README 에 "계층을 분리했습니다" 라고 쓰는 것과
위반이 컴파일되지 않는 것은 다르다.

부르는 말: "레거시 포팅", "새 구조로 옮겨줘", "모듈화해줘", "계층 분리"

### `skill-forge`

만든 스킬을 점검한다. **읽기 전용** — 고치지 않고 빠진 것만 보고한다.

기계 검사는 동봉한 스크립트가 한다.

```sh
./plugins/skill-forge/skills/skill-audit/audit.sh plugins
```

프론트매터, 실행 흐름, 멈추는 지점, 재개 지점, 폴백, 죽은 참조, 개인 경로,
트리거 겹침을 본다. 사람이 판단할 것(문장이 실제로 행동을 바꾸는지)은 판단하지 않고
그렇게 적는다.

**이 검사를 처음 돌렸을 때 대상 스킬보다 검사 자체의 결함이 먼저 나왔다** — 인용을 지시로 오판,
단계 표기 형식 누락, 동봉 파일과 대상 프로젝트 파일 혼동, 읽기 전용 패턴 과탐.
그래서 절차에 순서를 박았다: **대상을 고치기 전에 검사를 고친다.**

부르는 말: "스킬 평가해줘", "이 스킬 뭐가 부족해?"

### `ios-measure`

성능 문제를 **추측으로 고치지 않게** 순서를 강제한다.

```
재현 → 계측 → 측정 → 수정 → 재측정
```

- 계층별로 무엇을 재는지 표로 정리 — 네트워크 중복 요청 / 메인 스레드 점유(16.7ms) / 반복 경로 객체 생성
- 계측 코드는 `@autoclosure` + `#if DEBUG` 로 **릴리즈에서 문자열조차 만들지 않는다**
- 수치를 꺼내는 명령은 실재를 확인한 것만 넣었다 (`simctl launch --stdout=`,
  `SIMCTL_CHILD_` 환경변수 전달, `xcresulttool get log --type console`)

**가장 많이 틀리는 자리는 세는 지점이다.** 캐시 앞에서 세면 캐시를 넣어도 숫자가 그대로다.

부르는 말: "느리다", "왜 이렇게 오래 걸리지", "이거 재봐", "전후 비교"

### `code-lens`

읽기 전용 에이전트. 렌즈(로직 / 아키텍처 / 메모리·성능 / 테스트)를 지정하면 그 관점으로만 본다.

**렌즈를 좁히는 게 핵심이다.** 여러 관점을 한 번에 주면 아무것도 깊게 보지 않는다.
그리고 고치지 않는다 — 검토가 대상을 고칠 수 있으면 "고쳤으니 통과" 로 끝난다.

부르는 말: "개선점 찾아줘", "문제 있는 곳 찾아줘"

### `hiring-assignment`

과제 전형 3단계.

| 스킬 | 언제 |
|---|---|
| `assignment-start` | 받은 직후 30분 — 요구사항을 체크리스트로, 구조 결정, 시간 배분 |
| `assignment-submit` | 제출 직전 — clean clone 빌드, 잔재, 린트 원본 대비, **문서 수치 대조**, 압축 목록 |
| `assignment-critique` | 제출물을 이 대화를 못 보는 세션에 넘겨 적대적으로 평가받는다 |

#### `check.sh` 는 과제 밖에서도 쓴다

기계 검사 중 **과제 전용은 zip 규격 하나뿐**이고 나머지는 전부 범용이다.
그래서 **릴리즈·PR 점검용 스킬을 따로 만들지 않았다** — 복제하면 두 벌이 어긋난다.
스킬을 부르지 않고 스크립트만 돌려도 된다.

```sh
./plugins/hiring-assignment/skills/assignment-submit/check.sh <저장소경로> <앱스킴> [테스트스킴...]
```

| 검사 | 릴리즈 전에도 쓸모 |
|---|---|
| clean clone 빌드 | ○ 남의 머신에서 열리는지 |
| **문서 수치 대조** | ○ README·CHANGELOG 의 수치가 실제와 맞는지 |
| 린트 원본 대비 | ○ 내 포매터가 서식을 바꿨는지 |
| 커밋별 단독 빌드 | ○ 각 커밋이 스스로 서는지 |
| 문서 내부 참조 | ○ 깨진 링크·없는 절 |
| zip 규격 | ✗ 과제 전용 |

#### 채점 기준이 회사마다 다른 문제

평가 **절차**(열리는가 → 요구사항 → 실패 경로 → 구조 → 테스트 → 히스토리)는 어느 회사든 같다.
다른 것은 **무엇에 가중치를 두는가** 하나뿐이라 그것만 파일로 뺐다.

```
skills/assignment-critique/profiles/_template.md   ← 복사해서 채운다
```

양식의 핵심은 **확정도 표기**다.

- `[확정]` — 제출 안내·JD **원문**에 있는 말. 기본 가중치를 덮어쓴다
- `[추정]` — 블로그·발표에서 유추한 성향. 가중치를 못 덮고 동점일 때만 쓴다
- **빈칸은 비워 둔다.** 채워야 할 것 같아서 추측으로 메우면 채점표가 오염된다

프로필이 없으면 기본 가중치로 돌리고 **보고서 첫 줄에 그 사실을 적는다.**
없는 채점표를 지어내는 것이 기본값으로 도는 것보다 나쁘다.

## 만들 때 지킨 것

1. **읽기 전용을 강제한다.** 검토가 대상을 고칠 수 있으면 검토가 아니다
2. **렌즈를 하나로 좁힌다.** 여러 관점을 한 번에 주면 아무것도 깊게 보지 않는다
3. **차단하지 않는다.** 마감 직전에 도구가 작업을 막으면 사람이 도구를 끈다.
   발견한 것을 전부 보고하고 고칠지는 사람이 정한다
4. **오탐을 만들지 않는다.** 오탐이 나오면 검사를 끄고, 끄면 진짜를 놓친다
5. **회사·프로젝트마다 다른 것은 데이터로 뺀다.** 절차를 스킬에 두고 기준은 파일로 갈아끼운다
6. **확인한 것만 적는다.** 명령·API 이름은 실재를 확인한 뒤에 문서에 넣었다.
   코드블록은 붙여넣으면 돌아가는 것만 넣는다

## 한 벌만 둔다

스킬을 `~/.claude/skills/` 에도 두고 여기에도 두면 **반드시 어긋난다.**
플러그인으로 설치했으면 `~/.claude/` 쪽 사본은 지운다. 원본은 이 저장소 하나다.

```sh
ls ~/.claude/skills/     # 플러그인과 겹치는 것이 있는지 확인하고 지운다
```
