# 과제 제출 점검

제출 마감 30분 전에 도는 절차다. **여기서 발견되는 것은 대부분 되돌릴 수 없는 종류다** —
남의 머신에서 안 열리는 프로젝트, 템플릿 도메인 이름이 남은 파일, 빈 README.

## 원칙

- **차단하지 않는다.** 발견한 것을 전부 보고하고, 고칠지는 사용자가 정한다. 마감 직전에
  도구가 작업을 막으면 도구를 끄게 된다.
- **본 것만 보고한다.** 스크립트가 실제로 돌린 것과 내가 눈으로 읽은 것을 구분해서 적는다.
- 시간이 없으면 **1단계만이라도 돌린다.** 나머지는 사람이 훑는 게 낫다.

## 어떻게 쓰나 — 실제 흐름

```
사용자: "제출 전에 확인해줘"  (마감 1시간 전)
   │
   ├─ 1단계  기계 검사를 먼저 걸어 둔다 ───────────▶ 결과를 사용자가 본다
   │          clean clone → 생성 → 빌드 → 테스트       ■ 여기서 멈춘다
   │          가장 오래 걸리므로 제일 먼저 시작한다     고칠지는 사용자가 정한다
   │
   ├─ 2단계  잔재 검사 (템플릿 도메인·목업 URL·
   │          참조 0건·내부 문서·TODO)
   │
   ├─ 3단계  README — `[[ ]]` 잔여, 첫 화면,
   │          "왜 이 구조인가 / 일부러 안 한 것 /
   │           시간이 더 있으면"
   │
   ├─ 4단계  커밋 히스토리 ───────────────────────▶ 사용자가 판단
   │          커밋별 단독 빌드는 서브에이전트에         ■ 여기서 멈춘다
   │          넘긴다 (커밋 20개면 15분짜리다)          남은 시간에 넣을지 먼저 묻는다
   │
   ├─ 5단계  린트 경고 수를 원본 커밋과 비교
   │          내 포매터가 남의 서식을 바꿨는지
   │
   ├─ 6단계  문서에 적은 수치를 전부 다시 잰다
   │          잰 뒤에 코드가 또 움직였을 수 있다
   │
   │        여기까지의 발견을 「보고 형식」 으로 낸다 ─▶ 사용자가 수정 범위를 정한다
   │                                                   ■ 여기서 멈춘다
   │
   └─ 7단계  압축 ────────────────────────────────▶ 사용자 승인 뒤에만
              규격·제외 목록을 확인받고 만든다          ■ zip 은 되돌리기 어렵다
```

**멈추는 지점이 넷이다.** 1단계 결과를 본 뒤, 커밋별 단독 빌드를 돌리기 전,
수정 범위를 정하기 전, 그리고 **압축 전**.

멈추는 이유는 원칙과 같다 — **이 스킬은 차단하지 않는다.** 발견을 전부 내놓고,
마감까지 남은 시간에 무엇을 고칠지는 사용자가 정한다. 내가 대신 고르면 정작 중요한 것을
못 고친 채 시간이 끝난다.

**7단계는 특히 승인 뒤에만 한다.** zip 은 파일로 남고, 제출 규격을 틀리거나 빠져야 할 파일이
섞이면 이미 나간 뒤에 알게 된다. 만들기 전에 규격과 제외 목록을 눈으로 확인받는다.

### 점검 결과는 파일로 남긴다 — 재개 지점

`.claude/assignment-submit/<과제이름>.md` 에 적는다. **추적되는 경로에 두지 않는다** —
점검 기록이 제출물에 섞이면 2단계에서 스스로 잡아야 하는 항목이 된다.

1단계 clean clone 빌드는 길다. 그 사이에 대화가 끊기면 "어디까지 봤는지" 와 "무엇을 고치기로
했는지" 가 사라지고, 마감 직전에 처음부터 다시 돌리게 된다. 기억으로 이어가지 않는다.

```markdown
## 대상
저장소 경로 / 앱 스킴 / 테스트 스킴 / 제출 마감 시각

## 진행
- [x] 1단계 기계 검사   → clean clone 빌드 통과, 테스트 통과, 린트 error 0
- [x] 2단계 잔재 검사   → 템플릿 도메인 2곳 (아래)
- [ ] 3단계 README      ← 여기서 멈췄다
- [ ] 4단계 커밋 히스토리
- [ ] 5단계 린트 원본 대비
- [ ] 6단계 문서 수치 재측정
- [ ] 7단계 압축

## 발견 (고칠지 미정인 것 포함)
| 항목 | 단계 | 사용자 판단 |
|---|---|---|
| 템플릿 도메인 이름이 파일명에 남음 | 2 | 고친다 |
| TODO 3건 | 2 | README 로 옮긴다 |

## 돌리지 않은 검사
- 커밋별 단독 빌드 — 시간이 없어 건너뛰기로 함
```

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| README 의 "왜 이 구조인가" 가 일반론이라 구조 자체를 평가받아야 한다 | 내 대화를 본 사람이 내 구조를 평가할 수 없다. 이 대화를 못 보는 쪽에 맡긴다 | `assignment-critique` |
| 요구사항 목록이 아직 실패 케이스까지 안 나뉘어 있다 | 제출 점검은 요구사항 누락을 잡는 절차가 아니다. 목록을 먼저 만든다 | `assignment-start` |
| 문서에 성능 수치를 적어 놨다 (6단계) | 잰 뒤에 코드가 움직였으면 다시 잰다. 비율만 적지 않고 절대값을 남긴다 | `ios-measure:measure-ios` |
| 이 절차 문서 자체를 고치게 됐다 | 절차 문서도 기계 검사를 통과한 뒤에 쓴다 | `skill-forge:skill-audit` |

같은 플러그인 안의 스킬은 이름 그대로, 다른 플러그인의 스킬은 `플러그인:스킬` 형식이다.
**호출에 실패하면 원칙만 적용하고 계속 간다.** 마감 직전에 스킬을 찾느라 시간을 쓰지 않는다.

## 1단계 — 기계 검사 (먼저, 시간이 걸린다)

```sh
~/.claude/skills/assignment-submit/check.sh <저장소경로> <앱스킴> [테스트스킴...]
```

이 스크립트가 하는 것:

1. **clean clone** — `git clone` 으로 임시 디렉토리에 받는다. 추적되지 않는 파일이 빠진
   상태에서도 도는지 보는 게 핵심이다. 내 머신에만 있는 파일에 기대고 있으면 여기서 드러난다.
2. `tuist install` → `tuist generate` → 빌드 → 테스트
3. 린트 error 수
4. 커밋되지 않은 변경, 추적되지 않는 파일 목록
5. 비밀값·인증서 패턴, 생성물(`*.xcodeproj`, `Derived/`) 이 추적되는지

빌드가 오래 걸리므로 **제출 1시간 전에는 한 번 돌려 둔다.** 마감 10분 전에 처음 돌리면
고칠 시간이 없다.

## 2단계 — 잔재 검사

스크립트가 후보를 뽑아 주지만, 판단은 내가 한다. 각 항목을 실제로 열어 보고 보고한다.

| 찾는 것 | 왜 |
|---|---|
| 템플릿 도메인 이름 (`Item`, `ItemList`, 템플릿 앱 이름) | 과제 도메인으로 안 바꾼 자리. 채점자가 바로 알아본다 |
| 목업 URL·스킴 (`example.com`, `preview://`) | 실제 API 로 안 바꾼 자리 |
| 참조 0건인 파일·타입 | 안 쓰는 코드가 남아 있는 것은 감점이다 |
| 내부 문서 (`docs/PLAN.md` 등) | 제출물에 들어가면 안 되는 작업 기록 |
| `TODO` / 주석 처리된 코드 | 남길 거면 README 의 "시간이 더 있으면" 으로 옮긴다 |

참조 0건 확인은 **타입명으로 전체 검색**해서 정의 파일 외에 나오는지 본다.
"안 쓰는 것 같다" 로 보고하지 않고 "타입명 검색 결과 정의 1곳" 처럼 범위를 함께 적는다.

## 3단계 — README

**`[[ ]]` 가 하나라도 남아 있으면 즉시 지적한다.** 제출용 README 틀에서 채우지 않은 자리다.

먼저 **첫 화면**을 본다. 실행 방법과 "30초 안에 확인하실 것" 이 스크롤 없이 보여야 한다.
Example 앱·경계 위반 빌드·테스트가 무엇을 보는지 — 이 셋은 리뷰어가 시키지 않으면 하지 않고,
안 하면 없는 것과 같다.

그리고 아래 셋이 **채워져 있는지** 본다. 비어 있거나 일반론이면 지적한다.

1. **왜 이 구조인가** — 요구사항 규모와 선택을 잇는 문장인가.
   "Clean Architecture 를 적용했습니다" 는 미달이다. "저장 수단이 바뀔 수 있어 데이터 계층에
   가뒀습니다" 처럼 이 과제의 조건과 이어져야 한다.
2. **일부러 안 한 것** ← 제일 중요하다. 비어 있으면 반드시 지적한다.
   안 한 것을 의도적으로 안 했다고 쓰는 순간 모르는 게 아니라 판단한 게 된다.
3. **시간이 더 있으면** — 남은 것을 솔직히. 빈칸으로 두지 않는다.

첫 줄에 **실행 방법**이 있는지도 본다. 프로젝트가 생성 기반이면 생성 명령과 도구 버전이
첫 화면에 보여야 한다. 채점자가 여는 데 마찰이 생기면 그 순간 손해다.

## 4단계 — 커밋 히스토리

```sh
git log --format='%h %s' | cat
```

- **커밋이 하나뿐이면 지적한다.** 기능 단위로 쪼개져 있어야 협업 가능한 사람으로 읽힌다.
- 템플릿을 썼다면 **첫 커밋 메시지에 그 사실이 있는지** 본다. 숨기면 히스토리에서 티가 나고,
  밝히면 자기 표준이 있는 사람으로 읽힌다.
- 메시지가 규칙을 따르는지 — `~/.claude/CLAUDE.md` §9.

### 커밋별 단독 빌드는 **서브에이전트에 넘긴다**

`.git` 을 함께 내는 과제는 "각 커밋이 단독으로 빌드된다" 를 요구하는 경우가 있다.
커밋 20개면 순차 빌드 15분짜리다. **메인 세션이 붙잡고 있을 일이 아니다.**

`isolation: "worktree"` 를 준 서브에이전트에 넘긴다. 워크트리가 격리돼 있으므로
에이전트가 checkout 을 반복해도 내 작업 트리가 흔들리지 않는다.

에이전트에게 줄 조건:

- `-derivedDataPath` 를 **한 곳으로 고정** — 증분 빌드가 되어 몇 배 빨라진다
- `-destination 'generic/platform=iOS Simulator'` — 시뮬레이터를 띄우지 않고 컴파일만 본다
- **테스트는 돌리지 않는다.** 빌드만 본다
- 코드를 고치지 말고, rebase 하지 말 것

같은 순회에서 커밋 메시지도 함께 검사시킨다 — 형식, 한 커밋 한 논리 변경,
**본문에서 주장한 것이 실제 diff 에 있는지.**

## 5단계 — 저장소 서식을 내 도구가 바꿔놓지 않았는지

**실전에서 실제로 당한 것이다.** 내 `PostToolUse` 포매터가 컬렉션 리터럴에 trailing comma 를
넣는데, 남의 저장소는 그 서식을 쓰지 않았다. 20곳이 바뀌어 diff 가 지저분해졌다.

원본 커밋과 지금을 **같은 린터로 재서 경고 수를 비교한다.**

```sh
FIRST=$(git log --format=%H | tail -1)      # 과제 원본 상태
swiftlint --quiet | grep -c warning         # 지금

git stash -u
git checkout -q "$FIRST"
swiftlint --quiet | grep -c warning         # 원본
git checkout -q -
git stash pop
```

- 원본보다 **늘었으면 어느 규칙이 늘었는지** 본다:
  `swiftlint --quiet | grep -oE '\([a-z_]+\)$' | sort | uniq -c | sort -rn`
- 원본에 0건이던 규칙이 생겼으면 **그건 내 도구가 넣은 것이다.** 되돌린다
- 원본이 이미 넘는 규칙(긴 줄 등)은 저장소 스타일이므로 건드리지 않는다
- 설정 파일(`.swiftlint.yml`)이 없으면 기본 규칙으로 재는 것이고, 그때 원본이 깨끗하지 않은
  것은 정상이다. **목표는 0이 아니라 원본과 동수다**

편집 도구(`Edit`/`Write`)를 쓰면 훅이 다시 포맷하므로, 되돌리기는 `Bash`(python/perl)로 한다.

## 6단계 — 문서가 주장하는 수치를 다시 잰다

**실전에서 가장 많이 당한 자리다.** 문서와 코드가 어긋난 것이 네 건이었고 원인은 하나였다 —
**잰 뒤에 코드가 또 움직였다.** 중간에 잰 수치는 제출 시점에 전부 거짓이 될 수 있다.

문서에 숫자를 적었으면 **제출 직전에 예외 없이 다시 잰다.**

```sh
git rev-list --count HEAD                        # 커밋 수
grep -rc '@Test\|func test' <테스트경로>/*.swift   # 선언된 테스트 수
xcodebuild test ... 2>&1 | grep 'Test run with'  # 실제 실행된 수 ← 선언 수와 다를 수 있다
swiftlint --quiet | grep -c warning
wc -l <문서에서 언급한 파일들>
```

**선언 수와 실행 수는 다르다.** 프로젝트 생성 도구를 쓰는 저장소에서 테스트 파일만 추가하면
타깃에 안 붙어 조용히 실행되지 않는다. 문서에 적는 것은 **실행된 수**다.

### 수치가 아닌 주장도 검증한다

| 문서에 이런 말이 있으면 | 확인 |
|---|---|
| "전수 확인했다" | 정말 전부 돌렸는지. 하나라도 건너뛰었으면 문장을 고친다 |
| "모든 커밋이 빌드된다" | 4단계 결과와 일치하는지 |
| "N% 개선" | 재현 절차와 함께 적혀 있는지. 비율만 있으면 절대값을 넣는다 |

### 문서 내부 참조를 눌러 본다

절 번호·앵커 링크가 실제로 존재하는 제목을 가리키는지 확인한다. 문서를 고치는 동안
제목이 바뀌면 링크만 남는다. **읽는 순서를 안내하는 링크가 깨져 있으면 안내가 없는 것보다 나쁘다.**

## 7단계 — 압축

과제마다 규격이 다르다. **안내 문서를 다시 읽고 그대로 맞춘다.** 흔한 항목:

| 확인 | 왜 |
|---|---|
| 파일명 규칙 | 지정된 형식이 있으면 글자 하나까지 맞춘다 |
| 용량 상한 | `DerivedData`·빌드 산출물이 섞이면 순식간에 넘는다 |
| `.git` 포함 여부 | 포함이면 `--exclude` 로 빼지 않도록 조심 |
| **gitignore 된 파일** | ← 가장 위험하다 |

**`.gitignore` 는 zip 을 막지 못한다.** 폴더째 압축하면 추적되지 않는 파일도 함께 들어간다.
작업용 메모·요구사항 정리·API 키가 그렇게 나간다.

압축 전에 반드시 본다.

```sh
git status --short --ignored | grep '^!!'    # 무시되지만 파일로 존재하는 것
```

여기 나온 것을 하나씩 판단하고, 들어가면 안 되는 것은 `zip -x` 로 명시적으로 뺀다.
`.gitignore` 에 있으니 괜찮다고 넘기지 않는다.

압축한 **뒤에** 목록을 확인한다. 만들기 전 의도가 아니라 결과를 본다.

```sh
unzip -l <파일>.zip | grep -iE '<빠져야 하는 이름>' || echo '없음 (정상)'
```

## 보고 형식

고칠 수 있는 것과 없는 것을 나눠 적는다. 남은 시간을 함께 고려해 우선순위를 매긴다.

```
■ 지금 고쳐야 (제출 차단급)
■ 고치면 좋음 (시간 되면)
■ 확인했고 문제 없음
```

마지막에 **내가 돌리지 않은 검사**를 명시한다. 시간이 없어 건너뛴 것이 있으면 그렇게 적는다.
