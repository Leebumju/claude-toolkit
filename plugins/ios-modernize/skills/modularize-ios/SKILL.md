# 모듈화

**README 에 "계층을 분리했습니다" 라고 쓰는 것과 위반이 컴파일되지 않는 것은 다르다.**
이 절차의 끝은 파일을 옮기는 것이 아니라 **위반 `import` 를 넣어 빌드가 죽는 것을 확인하는 것**이다.
그걸 안 하면 경계는 문서상의 약속일 뿐이다.

## 언제 하나 — 순서는 맞고 조건이 틀렸다

`기능 → 구조` 순서는 옳다. 기능이 흔들리는 상태에서 경계를 그으면 요구사항이 바뀔 때마다
다시 그어야 한다. 무엇이 공유물인지도 기능이 굳은 뒤에야 보인다.

**틀리는 것은 "시간 남으면" 이라는 조건이다.** 조건부로 두면 실제로는 시간의 끝에 하게 되고,
끝에 하면 배선을 마치지 못한다. 실측하면 중간 규모 앱에서 **20~30분**이다.
조건부로 둘 이유가 없는 크기다. **일정에 못 박고 시작한다.**

---

## 어떻게 쓰나 — 실제 흐름

```
사용자: "이 앱 모듈로 나눠줘"
   │
   ├─ 0단계  내가 4개를 묻는다 ──────────────▶ 사용자가 답한다
   │          (규모 · 도구 · 생성물 커밋 여부 · 목표)
   │
   ├─ 1단계  현재 의존 그래프를 실측해 보여준다
   │          누가 누구를 import 하는지 표
   │
   ├─ 2단계  경계 안을 낸다 ─────────────────▶ 사용자가 승인
   │          모듈 목록 + 무엇이 어디로 가는지    ■ 여기서 멈춘다
   │
   ├─ 3~4단계 아래 계층부터 만들고 옮긴다
   │          접근 수준 청구서를 처리한다
   │
   ├─ 5단계  위반 import 를 넣어 빌드를 죽인다 ─▶ 사용자가 빌드
   │          죽는 것을 확인하고 되돌린다        ■ 여기서 멈춘다
   │
   └─ 커밋 후보를 제시한다 ──────────────────▶ 사용자가 판단
```

**멈추는 지점이 세 곳이다.** 경계 승인 전, 경계 검증(빌드), 커밋 전.

2단계에서 승인을 받는 이유는 **모듈 이름과 범위가 사람의 판단이기 때문**이다.
무엇을 한 모듈로 볼지는 코드만 읽어서 나오지 않는다.

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| 옮기는 게 아니라 패턴까지 바꿔야 한다 | 구조 이동과 동작 변경을 같은 커밋에 섞지 않는다 | `legacy-port` (같은 플러그인) |
| 모듈 경계를 넘는 테스트가 깨진다 | 경계를 무르지 말고 테스트가 붙을 자리를 옮긴다 | `test-seams` (같은 플러그인) |
| 모듈화 후 빌드가 느려졌다 | 추측하지 않고 빌드 시간을 잰다 | `ios-measure:measure-ios` |

같은 플러그인 안은 이름 그대로, 다른 플러그인은 `플러그인:스킬` 형식이다.
**호출에 실패하면 원칙만 적용하고 계속 간다.**

## 0. 먼저 확인한다 — 사용자에게 묻는다

1. **규모** — 화면 몇 개인가. 화면 둘에 모듈 넷은 과설계다 (→ 2단계에서 정당화한다)
2. **도구** — Tuist / SPM 로컬 패키지 / 수동 타깃 중 무엇을 쓰는가. 이미 있으면 그것을 따른다
3. **생성물을 커밋하는가** — 프로젝트 생성 도구를 쓰면 `.xcodeproj` 를 커밋할지 정해야 한다.
   남이 도구 없이 열어야 하면 커밋한다 (→ 6단계)
4. **목표** — 빌드 시간인가, 경계 강제인가, 팀 분리인가. 목표가 다르면 자르는 선이 달라진다

## 1. 현재 의존 그래프를 실측한다

추측하지 않는다. **다만 재는 방법이 두 갈래다.** 어느 쪽인지 먼저 정한다.

### 이미 모듈이 있으면 — `import` 를 센다

```sh
grep -rn '^import ' --include='*.swift' . | grep -vE 'import (Foundation|UIKit|SwiftUI|Combine|os)$'
```

### 단일 타깃이면 — `import` 는 쓸모없다

**내부 `import` 가 존재하지 않으므로 서드파티 목록만 나온다.**
실제로 단일 타깃 저장소에서 위 명령을 돌려 보니 1,038줄이 나왔고 **전부 라이브러리**였다.
내부 의존은 한 줄도 안 나왔다. 그런데 이 스킬이 쓰이는 경우가 대개 이쪽이다.

단일 타깃에서는 **타입 참조**로 그래프를 그린다. 디렉토리가 모듈 후보다.

```sh
T=$(mktemp -d)

# 1) 디렉토리마다 그 안에서 선언한 최상위 타입 이름을 모은다
for d in <후보 디렉토리들>; do
  grep -rhoE '^(public |internal |final |open )*(class|struct|enum|protocol) [A-Z][A-Za-z0-9_]+' \
      "$d" --include='*.swift' | awk '{print $NF}' | sort -u > "$T/$(basename "$d").types"
done

# 2) A 가 선언한 타입을 B 의 몇 파일이 쓰는가 = B → A 의존
grep -rlwFf "$T/A.types" <B 디렉토리> --include='*.swift' | wc -l
```

`-w`(단어 경계)와 `-F`(고정 문자열)를 반드시 붙인다. 없으면 부분 일치로 부풀어 오른다.

### 이 방법의 정확도를 먼저 확인한다

**타입 이름으로 세는 것이므로 두 가지가 숫자를 오염시킨다.** 재기 전에 확인한다.

```sh
# 두 디렉토리가 같은 이름의 타입을 선언하면 방향 판정이 무의미해진다
comm -12 "$T/A.types" "$T/B.types" | wc -l

# 흔한 단어가 타입 이름이면 오탐이 난다 (Item·Data·View·State 등)
grep -xE '(User|Item|Model|Data|State|Action|View|Cell|Row|Error|Result|Type|Key|Value|Service|Manager)' "$T/A.types"
```

**확인한 것** — 실제 저장소에서 겹치는 이름은 0개였고, 위험 단어는 `Item` 하나였다.
그것을 제외하고 다시 재니 96 → 95 로 **1파일만 움직였다.** 이 정도면 방법을 신뢰할 수 있다.
겹침이 많거나 위험 단어가 여러 개면 **그 이름들을 제외하고 다시 센 뒤 숫자를 보고한다.**

### 여기서 찾을 두 가지

- **순환** — A 가 B 를, B 가 A 를 참조하는 쌍. **이게 있으면 두 모듈로 가를 수 없다.**
  순환을 먼저 끊어야 3단계로 갈 수 있다
- **한쪽으로만 흐르는 것** — 이미 아래 계층인 것. 그게 첫 모듈 후보다

실제 저장소에서 나온 모양이다.

```
신규 디렉토리 → 레거시 디렉토리    95 파일
레거시 → 신규 디렉토리           152 파일   ← 양방향. 순환이다
양쪽 → 모델 디렉토리        942 + 181 파일   ← 공유물
양쪽 → 유틸 디렉토리        580 + 144 파일   ← 공유물
```

**순환을 만드는 것이 무엇인지까지 본다.** 이름을 뽑으면 2단계 경계 안이 바로 나온다.

```sh
grep -rhowFf "$T/A.types" <B 디렉토리> --include='*.swift' | sort | uniq -c | sort -rn | head
```

실제로 돌려 보니 상위가 **모델 타입과 공용 뷰**였다 (한 모델 46건, 다른 모델 30건,
공용 입력 뷰 22건). 그것들을 아래 계층으로 내리면 순환이 끊긴다 — 2단계의 규칙이
여기서 숫자로 확인된다.

## 2. 경계를 정한다 — 공유물 식별이 전부

기본형은 네 층이다. 이름은 저장소 관례를 따른다.

```
App          진입·조립만. 모든 피처를 알 수 있는 유일한 곳
 ├─▶ Feature  화면 하나와 그 로직. 서로를 모른다
 │     └─▶ Core        네트워크·저장·계측 + 여러 화면이 공유하는 상태
 │           └─▶ DesignSystem  토큰·공통 뷰. 외부 의존 0
```

### 규칙 — 여러 화면이 쓰면 피처가 아니다

가장 많이 틀리는 자리다. **새로 만든 화면만 모듈로 빼면** 곧 이렇게 된다.

```
FeatureA ──import──▶ FeatureB      ← 탭 A 가 탭 B 의 내부를 본다
```

경계를 세운 의미가 없다. 두 화면이 함께 쓰는 것(공유 상태, 공용 카드 뷰, 공용 모델)을
**아래로 내린 뒤**에야 방향이 정리된다.

```
FeatureA ──▶ Core ◀── FeatureB
```

**폴더 이름으로 그 사실을 남긴다.** `Core/Shared/` 처럼 "이건 공유물이라 아래 계층에 있다" 가
이름에서 보이면 다음 사람이 피처로 되돌리지 않는다.

### 이름·범위가 모호하면 묻는다

catch-all(`Utils`, `Common`, `Manager`)을 쪼갤 때 어느 모듈로 갈지 애매한 것이 반드시 나온다.
**혼자 정하고 넘어가지 않는다.** 목록으로 만들어 물어본다.

### 규모를 여기서 정당화한다

경계를 정하는 자리가 개수를 정당화하는 자리다. 다 만든 뒤에 세는 것이 아니다.
**모듈이 많다고 좋은 게 아니다.** 화면 둘에 모듈 넷이면 왜 그런지 답이 있어야 하고,
답이 없으면 판단력 없음으로 읽힌다.

모듈마다 한 줄로 답할 수 있어야 한다.

```
DesignSystem   외부 의존이 0인 것을 확인하고 가장 아래로 뒀다. 새 화면에서 토큰 참조 67건
Core           여러 화면이 쓰는 것은 피처가 아니다
Feature 3개    탭 단위. 서로를 모른다
```

한 줄이 안 나오는 모듈은 만들지 않는다. 그리고 다 만든 뒤에 **참조 0건인 모듈·타입이
남지 않았는지** 확인한다 — 타입명으로 전체 검색해서 정의 외에 나오는지 본다.
아무도 안 쓰는 것을 만들어 두는 것은 감점이다.

### 경계 안을 파일로 남긴다 — 재개 지점

승인받은 경계 안을 `.claude/module-plan.md` 에 적는다. **추적되는 경로에 두지 않는다.** **파일을 만든 뒤 그 파일이 실제로 안 뜨는지 확인한다.**

```sh
git status --porcelain <내가 만든 파일>   # 아무것도 안 나와야 한다
```

`git check-ignore` 만으로는 부족하다. 이유가 둘이다.

**하나 — 디렉토리로 물으면 답이 거꾸로 나온다.** 실측하면 이렇다.

```
git check-ignore -v .claude          → rc=1  (무시 안 됨으로 보인다)
git check-ignore -v .claude/x/y.md   → rc=0  (.gitignore 규칙을 짚는다)
```

디렉토리 자체는 무시 대상으로 보고되지 않는다. **파일로 물어야 규칙이 나온다.**

**둘 — `.gitignore` 에 있어도 이미 추적 중인 파일은 계속 추적된다.**
실제 저장소에서 `.claude/` 가 무시 대상인데 그 안에 추적 중인 파일이 10개 있었다.

그래서 **내가 만든 파일을 `git status --porcelain` 으로 직접 묻는다.** 그게 유일한 확답이다 — 없으면 작업 파일이 커밋 후보로 뜬다.

모듈화는 한 번에 끝나지 않고, 중간에 대화가 끊기면 "무엇을 어디로 옮기기로 했는지" 가 사라진다.
그때 기억으로 이어가면 승인받지 않은 배치가 섞인다.

```markdown
## 경계 (사용자 승인 2026-08-18)
DesignSystem ← 토큰, 공통 뷰
Core         ← 네트워크, 저장, 계측, 공유 상태(A/B 화면이 함께 쓰는 것)
FeatureA/B/C ← 탭별
App          ← 조립

## 진행
- [x] DesignSystem 분리
- [ ] Core 분리        ← 여기서 멈췄다
- [ ] Feature 분리
- [ ] 경계 검증 (위반 import)

## 아직 못 정한 것
- `Utils/DateHelper` → Core 인지 DesignSystem 인지 (물어야 함)
```

재개할 때는 이 파일을 먼저 읽는다.

## 3. 아래에서 위로 만든다

위에서 시작하면 아래가 흔들릴 때마다 다시 만든다.

```
DesignSystem → Core → Feature → App
```

- 의존성을 **문자열로 적지 않는다.** enum·상수로 두면 오타로 인한 잘못된 방향을 컴파일이 막는다
- 소스 글로브를 `Sources/**` 로 두면 하위 폴더가 자동으로 잡힌다. 파일 목록을 손으로 관리하지 않는다
- 한 모듈에 파일이 10개를 넘으면 **모듈 안을 폴더로 나눈다.** 경계를 갈랐어도 안이 평평하면
  원래 문제가 그대로다 (`Screen/` `Views/` `Model/` 처럼 역할이 이름에서 보이게)

## 4. 접근 수준 청구서를 처리한다

경계를 세우면 **미뤄 둔 계약이 한꺼번에 청구된다.** 한 타깃에 뭉쳐 있을 때는 컴파일러가 묻지 않던 것들이다.

| 나오는 요구 | 왜 |
|---|---|
| `public` | 모듈 밖에서 쓰는 타입·함수·생성자 전부 |
| `open` | 다른 모듈에서 상속하는 클래스 |
| `public required init?(coder:)` | 상속 가능한 UIKit 서브클래스 |
| `Sendable` | 공개 타입이 동시성 경계를 넘으면. 저장 프로퍼티 타입까지 따라온다 |

### 여기서 하지 말 것

**일괄 치환(sed·정규식)으로 `public` 을 붙이지 않는다.** 함수 안의 지역 변수까지 `public let` 이 되고,
타입 이름 일부만 겹치는 심볼이 함께 바뀐다. 실제로 `appendSections` 가
`appendXxxSections` 로 바뀌어 컴파일이 깨진 적이 있다. **필요한 선언만 하나씩 고친다.**

### 부수 효과 — 파일 분리가 쉬워진다

파일을 나누려면 `private` 을 모듈 내부(`internal`)로 풀어야 한다. 경계가 없을 때는
그게 곧 **공개 API 유출**이었다. 모듈이 있으면 `internal` 은 모듈 안에서만 보인다.
즉 모듈화가 파일 분리를 **가능하게** 만든다. 순서가 거꾸로가 아니다.

## 5. 경계를 검증한다 — 이 단계가 목적이다

**위반을 써 보고 빌드가 죽는지 본다.** 이것 말고 확인 방법은 없다.

```swift
// FeatureA 의 아무 파일 맨 위에 넣는다
import FeatureB
```

```
error: Unable to find module dependency: 'FeatureB'
```

이 에러가 나오면 경계가 진짜다. **나오지 않으면 "분리했다" 는 주장은 거짓이다.**
확인한 뒤 그 줄을 지운다.

검증할 방향을 빠뜨리지 않는다.

- 피처 → 다른 피처 (서로 모르는지)
- 아래 계층 → 위 계층 (`Core` 가 `Feature` 를 못 보는지)
- 가장 아래 모듈의 외부 의존이 0인지

빌드는 사용자가 돌린다. **내가 돌리지 않았으면 돌리지 않았다고 적는다.**

---

## 6. 생성 상태의 함정

프로젝트 생성 도구를 쓰면 여기서 조용히 틀린다.

| 증상 | 원인 | 대응 |
|---|---|---|
| 새로 만든 테스트가 **실행되지 않는다** (실패도 안 함) | 파일만 추가하고 프로젝트를 재생성하지 않음 | 재생성 후 **실행된 개수를 눈으로 확인** |
| 링크 단계에서 `framework not found` | 워크스페이스가 아니라 프로젝트만 지정해 빌드 | `-workspace` 로 빌드 |
| `Unexpected duplicate tasks` | 생성 상태가 낡음 | 생성물·파생 디렉토리를 지우고 재생성 |
| 남의 머신에서 열리지 않는다 | 생성물을 커밋하지 않음 | 커밋하거나 README 에 생성 명령을 적는다 |

**테스트 개수는 선언 수가 아니라 실행 수를 본다.** 둘은 다를 수 있다.

## 7. 보고 형식

```
■ 만든 모듈과 근거
   모듈명 → 담은 것 → 왜 이 층인지 (한 줄)

■ 옮긴 것
   무엇이 어디서 어디로 (공유물로 판정해 내린 것을 따로 표시)

■ 경계 검증
   피처↔피처 / 아래→위 / 최하위 외부의존
   각각 위반 import 를 넣어 확인했는지, 에러 메시지 원문

■ 접근 수준 변경
   public/open/Sendable 을 붙인 선언 수

■ 아직 정하지 못한 것
   이름·범위가 모호해서 물어야 하는 항목

■ 내가 돌리지 않은 것
   빌드·테스트를 돌렸는지. 안 돌렸으면 안 돌렸다고
```

커밋은 **모듈 단위로 쪼갠다.** 각 커밋이 단독으로 빌드되는지 확인한다 —
아래 계층 모듈부터 커밋하면 자연히 그렇게 된다.
