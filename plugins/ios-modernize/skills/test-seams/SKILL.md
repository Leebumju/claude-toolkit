# 테스트가 닿을 자리 만들기

**"테스트를 쓴다" 와 "테스트가 닿을 자리를 만든다" 는 다른 일이다.**
자리가 없는 코드에 테스트를 붙이면 닿는 곳만 검사하게 되고, 정작 틀리는 자리는 비어 있다.

가장 위험한 결과는 실패가 아니라 **초록이면서 아무것도 지키지 않는 테스트**다.
없는 것보다 나쁘다 — 있다고 착각하게 만든다.

실제로 이렇게 물렸다.

- 규칙을 검사하는 단위 테스트가 **전부 통과하는 동안 화면만 틀렸다.** 규칙은 맞고
  **규칙과 화면을 잇는 자리**가 틀렸는데, 그 자리가 뷰 컨트롤러 안이라 테스트가 닿지 못했다
- 배선하지 않은 복제본에 테스트 14개 중 약 10개가 단정하고 있었다. **전부 초록이었다**
- 테스트 파일을 추가했는데 타깃에 붙지 않아 **실패도 성공도 하지 않았다** (→ 5단계)

그래서 이 절차의 목적은 3단계다. **테스트가 닿을 자리를 만드는 것.**
붙인 테스트가 실제로 지키는지 확인하는 것은 `test-audit` 이 맡는다 (→ 4단계).

## 어떻게 쓰나 — 실제 흐름

```
사용자: "이 화면 테스트가 안 되는 구조야"
   │
   ├─ 0단계  내가 4개를 묻는다 ──────────────▶ 사용자가 답한다
   │          (대상 · 프레임워크 · 프로덕션 코드 변경 허용 · 시간)
   │
   ├─ 1단계  무엇이 안 닿는지 지도를 낸다
   │          닿지 않는 이유별로 분류
   │
   ├─ 2단계  무엇을 먼저 덮을지 순서를 낸다 ──▶ 사용자가 승인
   │          실패 경로부터. 개수가 아니라 선택      ■ 여기서 멈춘다
   │
   ├─ 3단계  자리를 만든다 (싼 것부터) ────────▶ 사용자가 승인
   │          프로덕션 코드가 바뀐다                ■ 여기서 멈춘다
   │
   ├─ 4단계  지키는지 확인 + 실행 수 대조 ─────▶ 사용자가 테스트 실행
   │          깊게 볼 것은 test-audit 으로 넘긴다
   │
   └─ 커밋 후보를 제시한다 ──────────────────▶ 사용자가 판단
```

**멈추는 지점이 셋이다.** 우선순위 승인 전, **프로덕션 코드를 고치기 전**, 커밋 전.

3단계에서 멈추는 이유가 중요하다. 자리를 만드는 것은 **테스트 코드가 아니라 프로덕션 코드를
바꾸는 일**이다. 테스트를 붙이려고 구조를 바꾸는 것이 허용되는지는 사람이 정한다.

### 기록은 파일로 남긴다 — 재개 지점

`.claude/test-seams/<대상>.md` 에 적는다. **추적되는 경로에 두지 않는다.** **파일을 만든 뒤 그 파일이 실제로 안 뜨는지 확인한다.**

```sh
git status --porcelain <내가 만든 파일>   # 아무것도 안 나와야 한다
```

`git check-ignore` 만으로는 부족하다. 이유가 둘이다.

**하나 — 디렉토리로 물으면 답이 거꾸로 나온다.** 실측하면 이렇다.

```
git check-ignore -v .claude          → rc=1  (무시 안 됨으로 보인다)
git check-ignore -v .claude/x/y.md   → rc=0  (.gitignore 규칙을 짚는다)
```

디렉토리 자체는 무시 대상으로 보고되지 않는다. **파일로 물어야 규칙이 나온다.**

**둘 — `.gitignore` 에 있어도 이미 추적 중인 파일은 계속 추적된다.**
실제 저장소에서 `.claude/` 가 무시 대상인데 그 안에 추적 중인 파일이 10개 있었다.

그래서 **내가 만든 파일을 `git status --porcelain` 으로 직접 묻는다.** 그게 유일한 확답이다 — 없으면 작업 파일이 커밋 후보로 뜬다.

닿지 않는 곳의 지도와 승인받은 우선순위가 이 절차의 자산이다.
대화가 끊긴 뒤 기억으로 이어가면 **승인받지 않은 구조 변경**이 섞인다.

```markdown
## 닿지 않는 것 (1단계)
| 대상 | 왜 안 닿나 | 자리를 만드는 방법 | 우선순위 |
|---|---|---|---|
| 검색 규칙 | 뷰 컨트롤러 안에 있다 | 순수 함수로 추출 | 1 |
| API 클라이언트 | 타입 안에서 직접 만든다 | 프로토콜 + 생성자 주입 | 2 |

## 승인받은 순서 (2단계, 2026-08-18)
1. 실패 → 재시도 복구
2. 검색 경계값 (0건 / 중복 키)

## 진행
- [x] 순수 함수 추출 + 테스트 6개
- [ ] 주입 자리 만들기   ← 여기서 멈췄다
- [ ] 실행 수 대조
- [ ] test-audit 로 신뢰도 검사 (별건)

## 붙인 테스트
- `SearchRuleTests` 6개 — 조작 미검증 (test-audit 로 넘길 것)
```

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| 자리를 만들려면 패턴까지 옮겨야 한다 | 동작 보존을 먼저 증명하고 나서 자리를 만든다 | `legacy-port` (같은 플러그인) |
| 모듈 경계를 넘어야 테스트가 닿는다 | 경계를 무르지 말고 테스트를 그 모듈 안으로 옮긴다 | `modularize-ios` (같은 플러그인) |
| 붙인 테스트가 정말 지키는지 봐야 한다 | 프로덕션을 깨서 빨개지는지 본다. 조작한 줄만 되돌린다 | `test-audit` (같은 플러그인) |
| 지켜야 할 것이 성능 수치다 | 수치를 먼저 재고 그 수치를 테스트로 못 박는다 | `ios-measure:measure-ios` |

같은 플러그인 안은 이름 그대로, 다른 플러그인은 `플러그인:스킬` 형식이다.
**호출에 실패하면 원칙만 적용하고 계속 간다.**

## 0. 먼저 확인한다 — 사용자에게 묻는다

1. **대상** — 화면 하나인가, 규칙 하나인가, 흐름 전체인가
2. **프레임워크** — 저장소가 이미 쓰는 것을 따른다 (→ 아래)
3. **프로덕션 코드를 바꿔도 되는가** — 이게 갈림길이다. 안 된다면 순수 함수 추출까지만 하고
   나머지는 "이 자리를 만들면 여기까지 닿는다" 로 보고만 한다
4. **시간** — 자리를 만들고 테스트를 붙이고 뒤집어 확인하는 데까지 걸린다.
   시간이 없으면 **자리만 만들고 테스트는 다음으로 남긴다**

### 프레임워크 갈림길

**저장소가 쓰는 것을 따른다.** 새로 고르는 것이 아니다.

| 상황 | 선택 |
|---|---|
| 기존 테스트가 `import XCTest` | XCTest 로 쓴다 |
| 기존 테스트가 `import Testing` | Swift Testing 으로 쓴다 |
| 테스트가 하나도 없다 | 신규 프로젝트면 Swift Testing, 오래된 저장소면 XCTest |

```sh
EX="--exclude-dir=build --exclude-dir=.build --exclude-dir=Derived --exclude-dir=checkouts --exclude-dir=vendor"
grep -rl '^import XCTest'  --include='*.swift' $EX "<앱 소스 루트>" | wc -l
grep -rl '^import Testing' --include='*.swift' $EX "<앱 소스 루트>" | wc -l
```

**제외 인자 없이 저장소 루트에서 돌리면 답의 대부분이 남의 코드다.**
실측하면 `XCTest` 2,758건이 나오는데 내역이 **빌드 산출물 1,959 / 워크트리 742 /
실제 테스트 타깃 51** 이었고, `Testing` 40건은 **전부 서드파티 체크아웃의 자체 테스트**였다.
그 숫자를 표에 물리면 **없는 Swift Testing 을 고른다.** 제외 인자를 붙이면 **53 / 0** 이 되어
표가 바로 답을 준다.

**히트 경로를 먼저 눈으로 본다.** `| wc -l` 앞에 `| head` 를 붙여 어디서 나오는지 확인한다.

| 상황 | 선택 |
|---|---|
| 한쪽이 0 | 0이 아닌 쪽 |
| **둘 다 0이 아니다** | **압도적인 쪽을 따른다.** 새 파일만 소수 쪽으로 쓰지 않는다 — 한 타깃에 섞는 것이 되는지 확인되지 않았다 |
| 둘 다 0 | 아래 판정표 |

**한 타깃에 둘을 섞을 수 있는지는 확인하지 못했다.** 내가 본 저장소들은 전부 한쪽만 쓴다
(레거시 51파일 XCTest / 신규 저장소 Swift Testing). 섞어야 한다면 **파일 하나로 먼저
확인하고 나서** 나머지를 옮긴다. 추측으로 전부 옮기지 않는다.

## 1. 무엇이 안 닿는지 지도를 만든다

커버리지 숫자를 재는 단계가 아니다. **닿지 않는 이유**를 분류하는 단계다.
이유마다 자리를 만드는 방법이 다르다.

| 닿지 않는 이유 | 어떻게 찾나 |
|---|---|
| **전역 상태를 직접 잡는다** | `.shared` / `singleton` 참조를 센다 |
| **의존성을 타입 안에서 만든다** | 생성자에 없는데 본문에서 `SomeClient()` 하는 곳 |
| **규칙이 화면 안에 있다** | 뷰·뷰 컨트롤러 파일의 조건문·계산 |
| **시간·랜덤·기기 상태에 의존** | `Date()` `random` `UIDevice` `UserDefaults` 직접 호출 |
| **결과가 화면에만 남는다** | 반환값 없이 뷰 프로퍼티만 바꾸는 함수 |

**`<대상>` 은 모듈 디렉토리 하나다. 저장소 루트를 넣지 않는다.**
루트를 넣고 돌리면 빌드 산출물·의존성 체크아웃이 섞여 수천 줄이 쏟아진다 —
실측한 저장소는 루트 기준 한 명령이 7,874줄을 냈고 대부분이 산출물이었다.
**공백이 있는 경로는 반드시 인용부호로 감싼다.**

```sh
D="<모듈 디렉토리>"
EX="--exclude-dir=build --exclude-dir=.build --exclude-dir=Derived --exclude-dir=checkouts --exclude-dir=.claude"

# 전역 상태 — 개수가 아니라 어느 싱글턴인지를 본다
grep -rhoE '\b[A-Z][A-Za-z0-9]*\.(shared|sharedInstance)\b' --include='*.swift' $EX "$D" \
    | sort | uniq -c | sort -rn
```

**`wc -l` 로 총계만 내지 않는다.** 실측한 저장소는 총 1,849건이었는데
리시버별로 집계하니 **최상위 하나가 68%(1,254건)** 였다. 판단 근거는 그 분포다.

```sh
# 타입 안에서 의존성을 만드는 곳 — suffix 를 먼저 세서 정규식에 넣는다
grep -rhoE '\b[A-Z][A-Za-z0-9]*(Service|Manager|UseCase|Repository|Wireframe|Presenter|Interactor|Provider|Store|Client)\b' \
    --include='*.swift' $EX "$D" | sed 's/.*[a-z]//' | sort | uniq -c | sort -rn
```

**suffix 목록을 고정하지 않는다.** 실측한 저장소에 `Client` 로 끝나는 타입은 **0개**였다 —
죽은 항목이다. 실제 조립 지점은 `Service` 313 · `Wireframe` 257 · `Presenter` 252 ·
`Interactor` 249 종이었고, 원래 정규식은 **그 셋을 다 놓쳐서 레거시 조립 지점 903건이
통째로 사각지대**였다. **0인 suffix 는 빼고, 상위에 있는 것을 넣는다.**

그리고 **두 결함을 한 바구니에 담지 않는다.**

```sh
grep -rnE '= [A-Z][A-Za-z0-9]*(<위에서 확인한 suffix>)\(' --include='*.swift' $EX "$D" | grep -v 'init('
#   → 본문 생성. 이 단계의 대상이다

grep -rnE 'init\(.*: *[A-Z][A-Za-z0-9]* *= *[A-Z]' --include='*.swift' $EX "$D"
#   → 기본값 주입. 3-c 가 금지한 별 결함이므로 목록을 따로 만든다
```

```sh
# 규칙이 화면 안에 있는 곳 — 먼저 대상을 고른다
find "$D" \( -name '*View.swift' -o -name '*ViewController.swift' \) | while IFS= read -r f; do
    printf '%s %s\n' "$(grep -cE '\bif |\bguard |switch ' "$f")" "$f"
done | sort -rn | head

# 상위 파일의 줄을 **읽는다**
grep -nE '\bif |\bguard |switch ' "<상위 파일>"
```

**개수는 판정이 아니다.** 실측하면 521줄 뷰의 5건이 **전부 SwiftUI 언랩**이었고,
35건 중 진짜 규칙은 3~4줄이었다. 주석 처리된 코드와 시트 토글이 같은 무게로 잡히고,
파일이 길수록 숫자가 커져서 교란된다. **레이아웃 분기와 데이터 판정을 손으로 가른다.**

```sh
# 통제되지 않는 입력 — 경계를 붙인다
grep -rnE '(^|[^A-Za-z0-9_])(Date\(\)|UUID\(\))|\.random|UserDefaults\.standard|UIDevice\.current' \
    --include='*.swift' $EX "$D"
```

**경계가 없으면 메서드 이름을 잡는다.** `Date\(\)` 만 쓰면 `tapCoverageStartDate()` 같은
이름이 걸린다 — 실측 251건 중 22건(9%)이 그런 오탐이었다.
그리고 **`: Date = Date()` 처럼 파라미터 기본값 형태는 3-d 가 이미 끝난 자리**이므로 제외한다.
`UIDevice` 는 표에는 있고 명령에는 없었다 (실측 77건).

### 직접 호출이 적으면 래퍼를 의심한다

**전역 접근이 0에 가깝게 나오는 것은 "깨끗하다" 가 아니라 "다른 이름으로 있다" 다.**

실측한 저장소는 `UserDefaults.standard` 직접 호출이 **71건**뿐이었다.
그런데 전역 래퍼 싱글턴 하나를 통해 쓰고 있었고 그 참조가 **1,254건**이었다.
직접 호출만 찾는 명령은 래퍼가 있는 저장소에서 구조적으로 0에 가깝게 나온다.

**첫 명령(리시버별 집계)의 최상위 항목이 저장·시간·기기 상태를 감싸고 있는지 본다.**
감싸고 있으면 그것이 실제 대상이다.

**가장 중요한 항목은 규칙 위치와 통제되지 않는 입력이다.** 규칙이 화면 안에 있으면
규칙 테스트가 통과해도 화면이 틀릴 수 있다. 그게 이 스킬이 존재하는 이유다.

## 2. 무엇을 먼저 덮을지 고른다 — 개수가 아니다

**전부 성공 경로면 0점에 가깝다.** 순서는 이렇다.

| 순위 | 무엇 | 왜 |
|---|---|---|
| 1 | **실패 경로** | 서버 에러에 상태가 실패로 가고 사용자에게 무언가 보이는가 |
| 2 | **실패 뒤 재시도 복구** | 여기서 가장 많이 죽는다. 한 번 실패한 상태가 남아 재시도가 안 된다 |
| 3 | **취소·이탈** | 응답 대기 중 화면을 나가면 무엇이 취소되는가 |
| 4 | **중복 요청** | 같은 동작을 연타하면 요청이 두 번 나가는가 |
| 5 | **경계값** | 0건 · 중복 키 · 빈 문자열 · 한 글자 |

5번을 얕보지 않는다. 실제로 여기서 크래시 두 건이 나왔다 —
**중복 키로 사전을 만드는 곳**(서버가 같은 id 를 두 번 주면 프로그램이 멈춘다),
그리고 **없는 섹션에 항목을 묻는 곳**.

## 3. 자리를 만든다 — 싼 것부터

**위에서부터 시도한다. 아래로 갈수록 프로덕션 코드가 많이 바뀐다.**

### a. 순수 함수로 추출한다 (가장 싸다)

계산·판정·포맷은 화면을 몰라도 된다. 밖으로 빼면 그 자체로 테스트가 붙는다.

```swift
// 뷰 컨트롤러 안에 있던 판정을 밖으로
struct SearchRule {
    static func matches(_ item: Item, query: String) -> Bool { ... }
}
```

의존성이 없으므로 주입도 필요 없다. **여기까지만 해도 대부분의 규칙 버그가 잡힌다.**

### b. "무엇을 보여줄지" 를 상태의 파생값으로 올린다

**규칙과 화면을 잇는 자리**가 뷰 안에 있으면 테스트가 닿지 못한다.
그 자리를 상태의 계산 프로퍼티로 올리면 화면 없이 검증할 수 있다.

```swift
enum Notice { case loadFailed, empty }
enum Row { case notice(Notice), item(Item) }

struct ScreenState {
    var items: [Item] = []
    var query = ""
    var didFail = false
    var loadedOnce = false

    /// 무엇을 보여줄지는 상태의 파생값이다
    var rows: [Row] {
        if didFail, items.isEmpty { return [.notice(.loadFailed)] }
        if loadedOnce, items.isEmpty { return [.notice(.empty)] }
        return items.filter { SearchRule.matches($0, query: query) }.map(Row.item)
    }
}
```

`.map(Row.item)` 이다. **`.map(.item)` 은 컴파일되지 않는다** —
`map` 이 받는 것은 클로저이고 거기서 암묵 멤버 참조가 풀리지 않는다.

```
error: type '(Item) throws(E) -> Row' has no member 'item'
```

**주의 — 여기서 가장 큰 실패가 나왔다.** 파생값을 만들고 **화면을 그것에 연결하지 않으면**
같은 규칙이 두 곳에 존재하게 되고, 테스트는 출하되지 않는 쪽을 지킨다.
파생값을 만들면 **화면의 기존 계산을 지우고 그것을 쓰게 만드는 것까지가 한 작업이다.**

배선을 끝내지 못한 채로 멈추게 되면 **파생값을 지우거나, 배선이 안 됐다는 사실을 보고한다.**
어느 쪽인지는 사용자가 정한다. 남겨 둘 때는 보고에 이렇게 적는다 —
"`rows` 파생값을 만들었고 **화면 배선은 하지 않았다.** 지금 상태에서는 같은 규칙이 두 곳에 있다."
**배선 안 된 파생값에 테스트를 붙여 초록으로 만들지 않는다.** 그것이 이 스킬이 막으려는 실패다.

### c. 프로토콜 + 생성자 주입

네트워크·저장·시간처럼 **결과를 바꿔야 하는 것**에만 쓴다.

```swift
protocol ItemLoading { func load() async throws -> [Item] }

final class ViewModel {
    private let loader: ItemLoading
    init(loader: ItemLoading) { self.loader = loader }   // 기본값을 주지 않는다
}
```

**기본값을 주지 않는다.** `init(loader: ItemLoading = LiveLoader())` 로 두면
주입을 잊은 호출부를 컴파일러가 잡아주지 못한다.

**프로토콜을 먼저 꺼내지 않는다.** a·b 로 되는 것에 프로토콜을 씌우면 파일만 늘어난다.

### d. 시간·랜덤·기기 상태를 값으로 받는다

```swift
func greeting(at date: Date) -> String   // Date() 를 안에서 부르지 않는다
```

가장 싼 주입이다. 프로토콜 없이 파라미터 하나로 끝난다.

## 4. 붙인 테스트가 지키는지 확인한다 — `test-audit` 로 넘긴다

**테스트를 붙였다고 끝이 아니다.** 초록인데 아무것도 지키지 않는 테스트가
이 스킬이 막으려는 실패다.

확인 방법은 하나다 — **프로덕션 코드를 일부러 깨서 빨개지는지 본다.**
그 절차(조작 4종 · 사이클마다 되돌림 · 배선 여부로 판정)는 분량이 있어서
`test-audit` 에 따로 있다. 그쪽은 **프로덕션을 일시적으로 깨뜨리므로 별 승인이 필요하다.**

`test-audit` 이 없으면 최소한 이것만 지킨다.

- 붙인 테스트 하나를 골라 **그 테스트가 검사하는 프로덕션 한 줄을 반대로 바꿔 본다**
- 빨개지지 않으면 그 테스트는 지키는 게 없다. **초록이라고 남겨두지 않는다**
- 확인한 뒤 **조작한 그 줄만** 되돌린다. `git checkout -- <파일>` 은 쓰지 않는다 —
  HEAD 로 되돌려서 커밋 안 된 다른 작업까지 날린다
- 조작해 보지 않았으면 **"조작 미검증" 으로 보고한다**

그리고 **선언 수와 실행 수를 대조한다.** 두 값은 다를 수 있다.

```sh
grep -rhoE '@Test\b|func test[A-Za-z0-9_]*' --include='*.swift' "<테스트 루트>" | wc -l   # 선언
xcodebuild test ... 2>&1 | grep 'Test run with'                                          # 실행
```

**`<경로>/*.swift` 를 쓰지 않는다.** 글로브가 파일로 펼쳐져서 `-r` 이 죽는다 —
실측한 저장소는 테스트 파일 60개 중 최상위가 12개뿐이어서 글로브로 세면 **159**,
재귀로 세면 **768** 이었다. **79% 과소 집계**다. 대조의 한쪽이 그만큼 틀리면
**없는 경보를 울리거나 진짜 경보를 삼킨다.**

프로젝트 생성 도구를 쓰는 저장소에서 파일만 추가하면 타깃에 안 붙어
**실패도 성공도 하지 않는다.**

### 재생성해도 안 붙는 경우가 있다 — 제외 목록을 읽는다

**소스 목록이 글로브여도 그 옆에 명시적 제외 목록이 있을 수 있다.**
그러면 재생성해도 계속 안 붙는다 — 스킬이 "재생성하고 다시 센다" 로 끝나면 이것을 놓친다.

```sh
grep -rnE 'exclud|EXCLUDED_SOURCE|excluding' <프로젝트 생성 설정 파일>
```

실측한 저장소는 테스트 파일 **2개가 제외 목록에** 있었고, 그 안의 test 함수 **18개는
디스크에 선언돼 있고 절대 실행되지 않았다.** 제외된 이유가 설정 파일 주석에 적혀 있었다 —
mock 이 프로토콜 요구사항을 못 채워 컴파일이 안 되는 상태였고, **타깃에서 빠져 있어서
아무도 몰랐다.**

이것이 이 스킬 서두의 실패 사례 세 번째와 같은 유형이다.
**원인이 "재생성 안 함" 이 아니라 "제외돼 있음" 일 수 있다.**

## 5. 보고 형식

```
■ 닿지 않던 것과 이유
   대상 → 왜 안 닿았나 → 어떤 자리를 만들었나 (a/b/c/d 중 무엇)

■ 프로덕션 코드 변경
   무엇을 바꿨는지. b(파생값)를 썼으면 **화면 배선을 끝냈는지** 명시

■ 붙인 테스트
   실패 경로 / 재시도 / 취소 / 중복 / 경계값 중 무엇을 덮었는지
   개수가 아니라 무엇을 골랐는지 적는다

■ 지키는지 확인
   조작해 봤는지 / 안 했으면 "조작 미검증"
   선언 수와 실행 수, 다르면 그 원인
   깊게 볼 필요가 있으면 test-audit 으로 넘길 것을 명시

■ 남긴 것
   자리는 만들었지만 테스트를 못 붙인 곳
```

**빌드·테스트를 돌리지 않았으면 돌리지 않았다고 적는다.** 통과했다고 쓰지 않는다.
