# 테스트 신뢰도 검사

**테스트가 초록인 것은 아무 증거가 아니다.**

가장 위험한 것은 실패가 아니라 **초록이면서 아무것도 지키지 않는 테스트**다.
없는 것보다 나쁘다 — 있다고 착각하게 만들어서, 그 자리를 다시 보지 않게 한다.

실제로 이렇게 물렸다.

- 배선하지 않은 복제본에 테스트 14개 중 약 10개가 단정하고 있었다. **전부 초록이었다**
- 테스트 파일을 추가했는데 타깃에 붙지 않아 **실패도 성공도 하지 않았다**

이 절차는 **테스트를 새로 만들지 않는다.** 있는 것이 쓸모 있는지만 판정한다.
자리가 없어서 테스트를 못 붙이는 문제는 `test-seams` 가 다룬다.

---

## 어떻게 쓰나 — 실제 흐름

```
사용자: "커버리지는 높은데 버그가 나"
   │
   ├─ 0단계  내가 3개를 묻는다 ──────────────▶ 사용자가 답한다
   │          (대상 범위 · 프로덕션 조작 허용 · 시간)
   │
   ├─ 1단계  선언 수와 실행 수를 대조한다 ─────▶ 사용자가 테스트 실행
   │          다르면 여기서 끝날 수도 있다          ■ 여기서 멈춘다
   │
   ├─ 2단계  조작 대상을 골라 목록으로 낸다 ───▶ 사용자가 승인
   │          프로덕션 코드를 일시적으로 깬다        ■ 여기서 멈춘다
   │
   ├─ 3단계  한 사이클씩 돈다
   │          조작 1개 → 실행 요청 → 결과 → 되돌림 → diff 확인
   │
   └─ 4단계  판정 목록을 낸다 ────────────────▶ 사용자가 정한다
              지울 후보 / 다시 쓸 후보          ■ 지우지 않는다
```

**멈추는 지점이 셋이다.** 실행 수 대조 후, **프로덕션을 깨기 전**, 그리고 마지막 —
**테스트를 지우는 것은 내가 하지 않는다.**

2단계에서 멈추는 이유가 중요하다. 이 절차는 **프로덕션 코드를 일시적으로 깨뜨린다.**
무엇을 얼마나 깰지는 사람이 정한다.

### 기록은 파일로 남긴다 — 재개 지점

`.claude/test-audit/<대상>.md` 에 적는다. **추적되는 경로에 두지 않는다.**
`.gitignore` 에 `.claude/` 가 있는지 먼저 확인한다
(`git check-ignore -q .claude/x && echo 무시됨`). 없으면 먼저 추가한다.

**조작 중에 대화가 끊기는 것이 이 절차의 최대 위험이다.** 프로덕션이 깨진 상태로 남는다.
그래서 조작 내용과 되돌림 여부를 매 사이클 파일에 적는다.

```markdown
## 실행 수 대조 (1단계)
선언 87 / 실행 87 — 일치

## 조작 목록 (2단계, 승인 2026-08-19)
1. SearchRule.matches 조건 반전
2. ScreenState.rows 반환값을 [] 로

## 사이클 기록
| 조작 | 되돌림 | 빨개진 테스트 |
|---|---|---|
| 1 조건 반전 | ✅ diff 비었음 확인 | 4개 |
| 2 반환값 상수화 | ✅ | **0개** ← 지키는 게 없다 |
| 3 호출 제거 | ❌ **아직 되돌리지 않음** ← 여기서 멈췄다 |

## 판정
- `rowsTests` 4개 → 배선 확인 결과 **미배선 복제본에 단정**. 지울 후보
```

**되돌리지 않은 조작이 있으면 그것을 맨 위에 적는다.** 재개할 때 가장 먼저 되돌린다.

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| 조작할 자리가 화면 안에 있어 테스트가 닿지 않는다 | 자리를 먼저 만든다. 안 닿는 곳에 테스트를 붙여 초록으로 만들지 않는다 | `test-seams` (같은 플러그인) |
| 조작했더니 크래시한다 | 그것은 발견이다. 원인을 좁혀 별건으로 다룬다 | `crash-triage` (같은 플러그인) |
| 지켜야 할 것이 성능 수치다 | 수치는 조작으로 검증되지 않는다. 재서 확인한다 | `ios-measure:measure-ios` |

같은 플러그인 안은 이름 그대로, 다른 플러그인은 `플러그인:스킬` 형식이다.
**호출에 실패하면 원칙만 적용하고 계속 간다.**

## 0. 먼저 확인한다 — 사용자에게 묻는다

1. **대상 범위** — 테스트 전체인가, 특정 파일·타입인가.
   전체는 조작 사이클이 길어진다. 의심되는 곳부터 좁히는 것이 낫다
2. **프로덕션 코드를 일시적으로 깨도 되는가** — 이게 갈림길이다.
   안 된다면 1단계(실행 수 대조)까지만 하고 나머지는 보고만 한다
3. **시간** — 조작 하나에 테스트 한 번씩 돈다. 조작 4개면 테스트를 4번 돌려야 한다

---

## 1. 선언 수와 실행 수를 대조한다 (먼저)

**여기서 끝날 수도 있다.** 안 돌고 있는 테스트는 조작해도 아무 반응이 없다.

```sh
# 선언 수
grep -rc '@Test\|func test' <테스트 경로>/*.swift | awk -F: '{s+=$2} END {print s}'

# 실행 수 ← 문서와 보고에 쓸 값은 이것이다
xcodebuild test ... 2>&1 | grep 'Test run with'
```

두 값이 다르면 **테스트 파일이 타깃에 붙지 않은 것**이다. 프로젝트 생성 도구를 쓰는
저장소에서 파일만 추가하면 조용히 실행되지 않는다 — 실패도 성공도 하지 않는다.
프로젝트를 재생성하고 **다시 센다.**

실제로 이 함정에 걸려 테스트 여덟 개가 돌지 않았다. 재생성 후 실행 수가 67 → 87 로 뛰었다.

**차이가 있으면 그것부터 보고한다.** 조작은 그다음이다.

---

## 2. 조작 대상을 고른다

전부 조작하지 않는다. **의심되는 곳**을 고른다.

| 우선순위 | 무엇 | 왜 |
|---|---|---|
| 1 | 참조 0건인 타입·프로퍼티를 단정하는 테스트 | 출하되지 않는 쪽을 지키고 있을 가능성 |
| 2 | 단정이 `!= nil` · `count > 0` 처럼 약한 것 | 값이 틀려도 통과한다 |
| 3 | 최근에 추가된 테스트 | 배선을 끝내지 못한 채 붙였을 수 있다 |
| 4 | **한 번도 빨개진 적 없는 영역** | 실패한 적이 없다는 것은 지킨 적이 없다는 뜻일 수 있다 |

```sh
# 참조 0건 후보 — 테스트만 그 이름을 쓰고 있나
grep -rn '<타입·프로퍼티명>' --include='*.swift' . | grep -v Tests

# 약한 단정
grep -rnE '#expect\((!=|.*!= nil|.*\.count > 0|.*isEmpty == false)' --include='*.swift' <테스트 경로>
grep -rnE 'XCTAssertNotNil|XCTAssertTrue\(.*\.count' --include='*.swift' <테스트 경로>
```

**목록을 내고 승인받는다.** 프로덕션을 깨는 작업이므로 무엇을 얼마나 깰지 사람이 정한다.

---

## 3. 한 사이클씩 돈다 — 되돌림이 절차에 포함된다

조작 네 가지 중에서 고른다. **한 번에 하나씩** 한다.

| 조작 | 무엇을 잡나 |
|---|---|
| **조건을 반전한다** (`==` → `!=`, `if a` → `if !a`) | 분기를 검사하지 않는 테스트 |
| **반환값을 상수로 만든다** (`return []` / `return true`) | 계산을 검사하지 않는 테스트 |
| **호출을 지운다** (side effect 한 줄 제거) | 효과를 검사하지 않는 테스트 |
| **경계를 ±1 한다** (`>` → `>=`, `count` → `count - 1`) | 경계값을 검사하지 않는 테스트 |

한 사이클은 이렇다.

```
① 조작 전 diff 를 본다        git diff --stat     ← 커밋 안 된 작업이 있는지 확인
② 조작 1개를 적용한다
③ 사용자에게 테스트 실행을 요청한다
④ 결과를 받아 기록한다        빨개진 테스트 이름과 개수
⑤ 조작한 그 줄만 되돌린다
⑥ diff 가 ① 과 같은지 확인한다  git diff --stat
```

### 되돌릴 때 `git checkout -- <파일>` 을 쓰지 않는다

그 명령은 **HEAD 로** 되돌리므로 같은 파일에 있던 **커밋되지 않은 다른 작업까지 함께 날린다.**
조작한 한 줄만 역치환한다 — 조건 반전이었으면 반전을 다시 되돌리고,
상수화였으면 원래 식으로 돌린다.

**실제로 이 함정에 걸려 같은 파일의 다른 수정 두 건이 사라진 적이 있다.**
파일에 커밋되지 않은 작업이 없는 것이 확실할 때만 `git checkout --` 를 쓴다.

**⑥ 을 건너뛰고 다음 조작을 시작하지 않는다.** 조작이 쌓이면 어느 조작이
어느 테스트를 빨갛게 만들었는지 갈리지 않고, 프로덕션이 깨진 상태로 남을 위험이 커진다.

---

## 4. 판정 목록을 낸다 — 지우지 않는다

빨개지지 않은 테스트를 그 자리에서 지우지 않는다. **어느 쪽인지 먼저 가른다.**

| 확인 | 판정 |
|---|---|
| 그 테스트가 단정하는 심볼이 **출하 경로에 배선돼 있나** (타입·프로퍼티명으로 전체 검색해 화면 코드가 그것을 읽는지) | 배선 안 됨 → **지울 후보** |
| 배선은 됐는데 안 빨개졌다 | 단정이 약한 것 → **조작한 그 값을 직접 단정하도록 다시 쓸 후보** |

**둘 다 "후보" 다.** 테스트를 지우는 것은 이 절차의 승인 지점이 아니다.
목록으로 보고하고 사용자가 정한다. **초록이라고 조용히 남겨두지도 않는다.**

## 5. 보고 형식

```
■ 선언 수 / 실행 수
   두 값과, 다르면 그 원인

■ 조작 사이클
   조작 → 빨개진 테스트 수 → 되돌림 확인 여부
   되돌리지 않은 조작이 있으면 **맨 위에** 적는다

■ 지킬 것이 없는 테스트
   테스트 이름 / 배선 여부 / 지울 후보인지 다시 쓸 후보인지

■ 조작하지 못한 것
   왜 (자리가 없다 / 승인 범위 밖 / 시간)

■ 내가 돌리지 않은 것
   테스트를 몇 번 돌렸는지. 안 돌렸으면 안 돌렸다고
```

**"테스트가 신뢰할 만하다" 를 쓰기 전에 확인한다.** 조작해 보지 않은 영역은
검사하지 않은 것이고, 그렇게 적는다.
