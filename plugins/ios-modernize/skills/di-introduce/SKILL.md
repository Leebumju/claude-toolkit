# 주입 구조 도입

**먼저 규모를 잰다. 규모를 모르고 전략을 정하면 시작도 못 한다.**

실제 레거시 저장소를 재 보면 이런 수가 나온다.

```
싱글턴 참조 2,006건 / 471개 파일
그중 최다 하나가 1,284건 / 317개 파일
```

이 규모에서 "싱글턴을 주입으로 바꾼다" 는 **리팩토링이 아니라 이주 사업**이다.
한 번에 할 수 없고, 반쯤 하다 멈추면 두 방식이 섞인 채로 남는다.

그래서 이 절차의 1단계는 세는 것이고, **2단계는 "전부 바꾸지 않기로 결정하는 것"** 일 수 있다.

---

## 어떻게 쓰나 — 실제 흐름

```
사용자: "이 싱글턴 걷어내줘"
   │
   ├─ 0단계  내가 4개를 묻는다 ──────────────▶ 사용자가 답한다
   │          (왜 주입하나 · 대상 · 범위 · 동작 변경 허용)
   │
   ├─ 1단계  규모를 센다
   │          참조 수 · 파일 수 · 전이 의존
   │
   ├─ 2단계  규모에 맞는 전략을 낸다 ─────────▶ 사용자가 승인
   │          전면 전환 / 잎부터 / 경계만          ■ 여기서 멈춘다
   │
   ├─ 3단계  조립 지점을 하나 만든다
   │          "구현을 고르는 곳" 을 한 곳으로
   │
   ├─ 4단계  옮긴다 — 중간 상태를 견디게
   │          싱글턴과 주입이 공존하는 기간이 있다
   │
   ├─ 5단계  남은 직접 접근을 센다 ───────────▶ 사용자가 빌드
   │          줄었는지 숫자로 본다                ■ 여기서 멈춘다
   │
   └─ 커밋 후보를 제시한다 ──────────────────▶ 사용자가 판단
```

**멈추는 지점이 셋이다.** 전략 승인 전, 남은 수 확인, 커밋 전.

2단계에서 멈추는 이유가 이 스킬의 핵심이다. **전략을 잘못 고르면 작업이 끝나지 않는다.**
그리고 "전부 바꾸지 않는다" 도 정당한 결론이라, 그 판단은 사람이 해야 한다.

### 기록은 파일로 남긴다 — 재개 지점

`.claude/di/<대상>.md` 에 적는다. **추적되는 경로에 두지 않는다.**
**파일을 만든 뒤 그 파일이 실제로 안 뜨는지 확인한다.**

```sh
git status --porcelain <내가 만든 파일>   # 아무것도 안 나와야 한다
```

`git check-ignore` 만으로는 부족하다. 이유가 둘이다.

**하나 — 디렉토리로 물으면 답이 거꾸로 나온다.** 실측하면 이렇다.

```
git check-ignore -v .claude          → rc=1  (무시 안 됨으로 보인다)
git check-ignore -v .claude/x/y.md   → rc=0  (.gitignore 규칙을 짚는다)
```

디렉토리 자체는 무시 대상으로 보고되지 않는다. **파일로 물어야 규칙이 나온다.**

**둘 — `.gitignore` 에 있어도 이미 추적 중인 파일은 계속 추적된다.**
실제 저장소에서 `.claude/` 가 무시 대상인데 그 안에 추적 중인 파일이 10개 있었다.

그래서 **내가 만든 파일을 `git status --porcelain` 으로 직접 묻는다.** 그게 유일한 확답이다.

**이 작업은 중간 상태가 오래 간다.** 어디까지 주입이고 어디부터 싱글턴인지 기억으로
이어가면 두 방식이 섞인 자리를 놓친다.

```markdown
## 규모 (1단계 실측 2026-08-19)
| 싱글턴 | 참조 | 파일 | 전략 |
|---|---|---|---|
| A | 1,284 | 317 | 경계만 — 전환하지 않는다 |
| B | 178 | 62 | 잎부터 |
| C | 22 | 8 | 전면 전환 |

## 승인받은 전략 (2단계)
C 만 전면 전환. B 는 새 코드부터. A 는 손대지 않는다

## 진행
- [x] 조립 지점 생성
- [x] C 전환 (22 → 0)
- [ ] B 잎 3개      ← 여기서 멈췄다
- [ ] 남은 수 재측정

## 남은 직접 접근
C: 0 / B: 171 (7건 줄임) / A: 1,284 (의도적으로 유지)
```

**"의도적으로 유지" 를 명시한다.** 안 적으면 다음 사람이 미완성으로 읽고 이어서 건드린다.

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| 목적이 테스트를 붙이는 것이다 | 테스트가 닿을 자리를 만드는 것이 먼저다. 주입은 그 수단 중 하나다 | `test-seams` (같은 플러그인) |
| 주입하면서 화면 패턴까지 바꾼다 | 동작 보존을 먼저 증명한다. 섞지 않는다 | `legacy-port` (같은 플러그인) |
| 모듈 경계를 세우는 것이 본론이다 | 공유물을 아래로 내린다. 위반이 컴파일되지 않는지 확인한다 | `modularize-ios` (같은 플러그인) |
| 주입 뒤 성능이 달라졌다 | 추측하지 않고 전후를 잰다 | `ios-measure:measure-ios` |

같은 플러그인 안은 이름 그대로, 다른 플러그인은 `플러그인:스킬` 형식이다.
**호출에 실패하면 원칙만 적용하고 계속 간다.**

## 0. 먼저 확인한다 — 사용자에게 묻는다

1. **왜 주입하나** — 이유마다 필요한 범위가 다르다

   | 이유 | 필요한 범위 |
   |---|---|
   | 테스트 대체물을 넣고 싶다 | 그 화면·타입 하나면 된다 (→ `test-seams` 가 더 맞다) |
   | 모듈 경계를 넘어야 한다 | 경계에 걸린 것만 |
   | 런타임에 구현을 갈아야 한다 (저장소 교체 등) | 그 인터페이스 하나 |
   | 전역 상태를 줄이고 싶다 | **전면. 여기가 가장 크다** |

2. **대상** — 싱글턴 하나인가, 여러 개인가
3. **범위** — 저장소 전체인가, 특정 모듈인가
4. **동작을 바꿔도 되는가** — 기본값은 **아니다.** 주입은 구조 변경이고 동작은 그대로여야 한다

## 1. 규모를 센다 (건너뛰지 않는다)

**대상 경로를 명시한다.** 저장소 루트에서 돌리면 빌드 산출물·SPM 체크아웃·워크트리 사본이
섞인다 — 실측한 저장소는 앱 소스 4,250개인데 루트 기준 27,077개였고, 같은 명령이
**6배(12,803건)** 를 냈다. 아래 `SRC` 는 앱 소스 루트다.

```sh
SRC="<앱 소스 루트>"                    # 공백이 있으면 반드시 인용부호
PAT='\.(shared|sharedInstance|default)\b'   # ← 한 번만 정의하고 5단계도 이것을 쓴다

# 전체 규모
grep -rE "$PAT" --include='*.swift' "$SRC" | wc -l
grep -rlE "$PAT" --include='*.swift' "$SRC" | wc -l

# 타입별 참조 수 — head 로 자르지 않는다
grep -rhoE "\b[A-Z][A-Za-z]*$PAT" --include='*.swift' "$SRC" | sort | uniq -c | sort -rn
```

**`head -10` 을 쓰지 않는다.** 실측한 저장소는 앱 싱글턴 40종 중 **30종이 22건 이하**였다 —
전부 "전면 전환" 후보인데 상위 10개에 안 들어서 목록에서 사라진다.
**가장 쉬운 대상이 잘려 나간다.**

### 프레임워크 static 을 걸러낸다

`UIApplication.shared` · `NotificationCenter.default` · `FileManager.default` 같은
프레임워크 static 이 순위에 섞인다. 실측한 저장소 상위 10개 중 **3개가 그것**이었다.
전략표에 넣으면 프레임워크 타입에 전략을 배정하게 된다.

**저장소 안에 정의가 있는 타입만 남긴다.** 정의를 찾는 명령이 그 필터이기도 하다.

```sh
# 싱글턴 정의 위치 — 전이 의존 확인의 입력이다
grep -rnE 'static (let|var) (shared|sharedInstance)\b' --include='*.swift' "$SRC"

# 타입이 여러 파일에 쪼개져 있으면 한 파일만 봐서는 과소계상한다
grep -rnE '^(final )?(class|struct|enum|extension) <타입>\b' --include='*.swift' "$SRC"
```

### `.shared` 세 개로는 전역 접근을 다 세지 못한다

실측한 저장소에서 **누락된 형태들**이다. 하나는 자릿수를 틀리게 만들었다.

```sh
# ① 표준 라이브러리 전역 — 주입·테스트 관점에서 전부 전역이다
grep -rcE 'UserDefaults\.standard|DispatchQueue\.main|Calendar\.current|UIScreen\.main|Bundle\.main' \
    --include='*.swift' "$SRC"

# ② 파일 스코프 전역 별칭 — 맨 식별자라서 어떤 .shared grep 으로도 안 잡힌다
grep -rnE '^(let|var) [a-z][A-Za-z0-9]* *[:=]' --include='*.swift' "$SRC"

# ③ 프로토콜 익스텐션 세탁 ← 가장 큰 누락
grep -rnE 'var [a-z][A-Za-z0-9]*: *[A-Z][A-Za-z0-9]* *\{ *(return )?[A-Z][A-Za-z0-9]*\.(shared|sharedInstance)' \
    --include='*.swift' "$SRC"
```

**③이 자릿수를 바꾼다.** 실측한 저장소는 레거시 API 클라이언트를 이렇게 감싸고 있었다.

```swift
protocol ApiServiceType {
    var auth: LegacyApiClient { LegacyApiClient.sharedInstance }   // ← .shared grep 에 1건
}
```

`.shared` 로 세면 **1건**이다. 실제로는 그 프로토콜을 언급하는 파일이 **72개**,
`auth.` 호출이 **33건**이었다 — **약 72배 과소계상.**
전략표에 1건으로 넣으면 "전면 전환" 판정이 나오는데 실제 규모는 72파일이다.

**표보다 표에 넣는 숫자가 위험하다.** ③을 먼저 세고 나서 전략을 고른다.

### 전이 의존을 본다

```sh
grep -nE '\.(shared|sharedInstance)\b' "<정의 파일>"
```

여기서 나온 숫자를 **2단계 전략표에 그대로 넣는다.** 감으로 전략을 고르지 않는다.

## 2. 규모에 맞는 전략을 고른다 — 전부 바꾸는 게 목표가 아니다

| 참조 수 | 전략 | 무엇을 하나 |
|---|---|---|
| **30건 이하** | **전면 전환** | 싱글턴을 없애고 전부 주입으로. 한두 커밋에 끝난다 |
| **31 ~ 300건** | **잎부터** | 다른 것을 안 잡는 타입부터. 여러 커밋. 중간 상태가 생긴다 |
| **300건 초과** | **경계만** | **전환하지 않는다.** 새 코드와 모듈 경계에서만 주입받게 하고, 기존 호출부는 그대로 둔다 |

**구간에 틈을 두지 않는다.** 원래 `~20 / ~200 / 1,000+` 로 적었더니 실측 분포에서
44건·60건·90건 세 타입이 **어느 칸에도 안 떨어졌다.** 20 과 200 사이를 감으로 정하게 되고,
그건 이 스킬이 금지한 것이다. 위 구간은 실측 6개 타입 전부에 판정을 준다.

### 300건을 넘으면 왜 전환하지 않나

317개 파일을 고치는 변경은 **리뷰가 불가능하고 회귀 범위가 저장소 전체**다.
그리고 중간에 멈추면 두 방식이 섞인 채로 몇 달 간다. 얻는 것보다 잃는 것이 크다.

대신 **새로 만드는 코드가 싱글턴을 직접 잡지 못하게** 막는다.

```
기존 코드 ──▶ Singleton.shared         (그대로 둔다)
새 코드   ──▶ 주입받은 인터페이스 ──▶ 어댑터 ──▶ Singleton.shared
```

어댑터 하나가 싱글턴을 감싸고, 새 코드는 인터페이스만 안다.
**나중에 싱글턴을 없앨 때 고칠 곳이 어댑터 하나다.**

```swift
protocol SettingsStore { func value(for key: String) -> String? }

/// 레거시 싱글턴을 감싸는 어댑터. 새 코드는 이 프로토콜만 안다.
/// 싱글턴을 없앨 때 고칠 곳은 이 파일 하나다.
struct LegacySettingsStore: SettingsStore {
    func value(for key: String) -> String? { LegacySettings.shared.value(key) }
}
```

**이것을 "미완성" 으로 보고하지 않는다.** 규모를 재고 내린 결정이고, 기록에 그렇게 남긴다.

## 3. 조립 지점을 하나 만든다

**구현을 고르는 곳이 한 곳이어야** 주입의 값어치가 나온다.
여러 곳에서 각자 고르면 싱글턴과 다를 게 없다.

```swift
// 앱 진입부 한 곳에서만 등록한다
settingsStore = LegacySettingsStore()
itemClient    = LiveItemClient(baseURL: config.baseURL)
```

규칙 둘이다.

- **기본값을 주지 않는다.** `init(store: SettingsStore = LegacySettingsStore())` 로 두면
  주입을 잊은 호출부를 컴파일러가 잡아주지 못한다. 이주 중에는 이 유혹이 특히 강하다 —
  기본값을 주면 호출부를 안 고쳐도 컴파일되기 때문이다. **그게 이주가 멈추는 이유다**
- **조립 지점에 로직을 넣지 않는다.** 무엇을 고르는지만 있고 판단은 없어야 한다

## 4. 옮긴다 — 중간 상태를 견디게

**한 번에 다 못 바꾼다.** 싱글턴과 주입이 공존하는 기간이 반드시 있다.
그 기간을 견디게 만드는 것이 이 단계의 전부다.

| 규칙 | 왜 |
|---|---|
| **싱글턴을 지우지 않는다** (아직) | 남은 호출부가 컴파일 안 된다. 마지막에 지운다 |
| **잎부터 옮긴다** — 다른 싱글턴을 안 잡는 타입 | 전이 의존이 있으면 아래부터여야 한다 (**잎이 없을 수 있다** → 아래) |
| **한 커밋 = 한 타입** | 회귀가 나면 어느 전환이 원인인지 갈린다 |
| **각 커밋이 스스로 빌드된다** | 중간 상태가 깨져 있으면 되돌릴 수 없다 |

전환 중에는 **같은 값을 두 경로로 읽는 자리**가 생긴다. 그게 가장 위험하다 —
한쪽에서 쓰고 다른 쪽에서 읽으면 값이 어긋난다.

**`xargs` 를 쓰지 않는다. 그리고 stderr 를 죽이지 않는다.**

```sh
# 같은 싱글턴을 직접 접근하면서 주입도 받는 타입 — 섞인 자리다
grep -rlE '<인터페이스명>' --include='*.swift' "$SRC" | while IFS= read -r f; do
    grep -q '<싱글턴>\.shared' "$f" && echo "$f"
done
```

**이것이 이 스킬에서 가장 위험했던 결함이다.** 원래 명령은 이랬다.

```sh
grep -rln '...' . | xargs grep -ln '...' 2>/dev/null      # ✗ 쓰지 않는다
```

iOS 저장소는 디렉토리 이름에 공백이 흔하다. `xargs` 가 공백에서 경로를 쪼개서
전부 실패한다 — 실측하면 이렇게 나온다.

```
grep: My: No such file or directory
grep: App/AppDelegate.swift: No such file or directory
```

(`My App/AppDelegate.swift` 가 공백에서 쪼개진 결과다.)

그리고 **`2>/dev/null` 이 그 실패를 전부 삼켜서 "섞인 자리 0건" 이 된다.**
아무것도 검사하지 않았는데 합격 판정이 나온다. **거짓 합격이 검사 없음보다 나쁘다.**

`stderr` 를 죽이는 것을 절차에서 금지한다. 에러가 보여야 명령이 실패한 것을 안다.

**섞인 자리가 나오면 그 타입은 한쪽으로 몰아야 한다.** 남겨 두지 않는다.

### 잎이 없으면 — 순환을 먼저 끊는다

**"잎부터" 는 전이 의존이 나무일 때만 성립한다.** 실측한 저장소는 순환이었다.

```
DB 싱글턴 ──▶ 키체인 싱글턴 ──▶ DB 싱글턴        (양방향)
DB 싱글턴 ──▶ 자기 자신 · 푸시 서비스 2개
URL 매니저 ──▶ DB 싱글턴
```

**잎이 하나도 없다.** 이때 "잎부터" 는 답을 주지 못한다.

순환을 끊는 방법 둘이다.

| 방법 | 무엇 |
|---|---|
| **값을 추출해 주입** | A 가 B 에게서 필요한 것이 값 하나면, 타입을 주입하지 않고 그 값만 파라미터로 넘긴다. 의존이 사라진다 |
| **내부가 아니라 호출 경계에서 주입** | A·B 내부는 그대로 두고, **둘을 부르는 상위에서** 주입받게 한다. 순환은 남지만 새 코드가 그 순환에 들어가지 않는다 |

**순환을 끊지 못하면 그 타입들은 "경계만" 전략으로 보낸다.** 순환 안에서 전면 전환을
시도하면 어느 순서로도 중간 상태가 깨진다.

### 이 명령은 두 번째 타입부터 입력이 생긴다

**첫 타입에는 인터페이스가 아직 없으므로 결과가 항상 0건이다.**
실측한 저장소에서 상위 싱글턴 3개를 감싸는 프로토콜은 **하나도 없었다** —
당연히 0건이고, 그것을 "깨끗하다" 로 읽으면 틀린다.

첫 타입에는 대신 이것을 찾는다.

```sh
# 주입받는 init 이 있으면서 싱글턴도 직접 잡는 파일
grep -rlE 'init\([a-z][A-Za-z0-9]*: *[A-Z]' --include='*.swift' "$SRC" | while IFS= read -r f; do
    grep -q '\.\(shared\|sharedInstance\)' "$f" && echo "$f"
done
```

실측하면 이쪽에서 2건이 나왔고, 하나는 **주입 + 직접 접근 + 기본값 인자**가
겹친 사례였다 — 3단계가 금지한 것 셋이 한 파일에 있었다.

## 5. 남은 직접 접근을 센다

**"주입 구조로 바꿨다" 를 숫자로 말한다.**

```sh
# 1단계에서 정의한 $PAT 과 $SRC 를 그대로 쓴다. 다른 정규식을 쓰면 안 된다
grep -rhoE "\b[A-Z][A-Za-z]*$PAT" --include='*.swift' "$SRC" | sort | uniq -c | sort -rn
```

**1단계와 정규식이 다르면 가짜 개선이 나온다.** 원래 1단계는
`shared|sharedInstance|default` 로 세고 5단계는 `shared|sharedInstance` 로 셌다.
실측하면 **2,463 → 1,944**, 아무것도 고치지 않았는데 **519건이 줄어 보인다.**
그래서 `$PAT` 을 한 번만 정의하고 두 단계가 같은 것을 쓴다.

전후를 나란히 적는다.

```
              전      후
타입 C        22       0    전면 전환 완료
타입 B       178     171    잎 3개 전환
타입 A     1,284   1,284    의도적으로 유지 (경계 전략)
```

**줄지 않은 것에 이유를 적는다.** 숫자만 내고 이유가 없으면 미완성으로 읽힌다.

빌드는 사용자가 돌린다. **내가 돌리지 않았으면 돌리지 않았다고 적는다.**

## 6. 보고 형식

```
■ 규모 (실측)
   싱글턴별 참조 수 · 파일 수 · 전이 의존

■ 고른 전략과 근거
   전면 / 잎부터 / 경계만 — 규모 숫자와 함께

■ 조립 지점
   어디 한 곳인지. 기본값을 주지 않았는지

■ 전후 숫자
   싱글턴별 전 → 후. **줄지 않은 것에 이유**

■ 섞인 자리
   직접 접근과 주입을 동시에 하는 타입이 남았는지 (남으면 위험)

■ 의도적으로 남긴 것
   "미완성" 이 아니라 "결정" 이라는 것을 명시

■ 내가 돌리지 않은 것
   빌드·테스트를 돌렸는지
```

**"싱글턴을 걷어냈다" 를 쓰기 전에 5단계 숫자를 본다.**
줄지 않았는데 그렇게 쓰면, 다음 사람이 끝난 작업으로 알고 넘어간다.
