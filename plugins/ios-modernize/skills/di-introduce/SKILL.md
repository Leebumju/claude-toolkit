# 주입 구조 도입

**먼저 규모를 잰다. 규모를 모르고 전략을 정하면 시작도 못 한다.**

실제 레거시 저장소를 재 보면 이런 수가 나온다.

```
싱글턴 참조 2,006건 / 471개 파일
그중 최다 하나가 1,284건 / 317개 파일
```

이 규모에서 "싱글턴을 주입으로 바꾼다" 는 **리팩토링이 아니라 이주 사업**이다.
한 번에 할 수 없고, 반쯤 하다 멈추면 두 방식이 섞인 채로 남는다.

그래서 이 절차의 1단계는 세는 것이고, **2단계는 "전부 바꾸지 않기로 결정하는 것"** 일 수 있다.

---

## 어떻게 쓰나 — 실제 흐름

```
사용자: "이 싱글턴 걷어내줘"
   │
   ├─ 0단계  내가 4개를 묻는다 ──────────────▶ 사용자가 답한다
   │          (왜 주입하나 · 대상 · 범위 · 동작 변경 허용)
   │
   ├─ 1단계  규모를 센다
   │          참조 수 · 파일 수 · 전이 의존
   │
   ├─ 2단계  규모에 맞는 전략을 낸다 ─────────▶ 사용자가 승인
   │          전면 전환 / 잎부터 / 경계만          ■ 여기서 멈춘다
   │
   ├─ 3단계  조립 지점을 하나 만든다
   │          "구현을 고르는 곳" 을 한 곳으로
   │
   ├─ 4단계  옮긴다 — 중간 상태를 견디게
   │          싱글턴과 주입이 공존하는 기간이 있다
   │
   ├─ 5단계  남은 직접 접근을 센다 ───────────▶ 사용자가 빌드
   │          줄었는지 숫자로 본다                ■ 여기서 멈춘다
   │
   └─ 커밋 후보를 제시한다 ──────────────────▶ 사용자가 판단
```

**멈추는 지점이 셋이다.** 전략 승인 전, 남은 수 확인, 커밋 전.

2단계에서 멈추는 이유가 이 스킬의 핵심이다. **전략을 잘못 고르면 작업이 끝나지 않는다.**
그리고 "전부 바꾸지 않는다" 도 정당한 결론이라, 그 판단은 사람이 해야 한다.

### 기록은 파일로 남긴다 — 재개 지점

`.claude/di/<대상>.md` 에 적는다. **추적되는 경로에 두지 않는다.**
`.gitignore` 에 `.claude/` 가 있는지 먼저 확인한다
(`git check-ignore -q .claude/x && echo 무시됨`). 없으면 먼저 추가한다.

**이 작업은 중간 상태가 오래 간다.** 어디까지 주입이고 어디부터 싱글턴인지 기억으로
이어가면 두 방식이 섞인 자리를 놓친다.

```markdown
## 규모 (1단계 실측 2026-08-19)
| 싱글턴 | 참조 | 파일 | 전략 |
|---|---|---|---|
| A | 1,284 | 317 | 경계만 — 전환하지 않는다 |
| B | 178 | 62 | 잎부터 |
| C | 22 | 8 | 전면 전환 |

## 승인받은 전략 (2단계)
C 만 전면 전환. B 는 새 코드부터. A 는 손대지 않는다

## 진행
- [x] 조립 지점 생성
- [x] C 전환 (22 → 0)
- [ ] B 잎 3개      ← 여기서 멈췄다
- [ ] 남은 수 재측정

## 남은 직접 접근
C: 0 / B: 171 (7건 줄임) / A: 1,284 (의도적으로 유지)
```

**"의도적으로 유지" 를 명시한다.** 안 적으면 다음 사람이 미완성으로 읽고 이어서 건드린다.

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| 목적이 테스트를 붙이는 것이다 | 테스트가 닿을 자리를 만드는 것이 먼저다. 주입은 그 수단 중 하나다 | `test-seams` (같은 플러그인) |
| 주입하면서 화면 패턴까지 바꾼다 | 동작 보존을 먼저 증명한다. 섞지 않는다 | `legacy-port` (같은 플러그인) |
| 모듈 경계를 세우는 것이 본론이다 | 공유물을 아래로 내린다. 위반이 컴파일되지 않는지 확인한다 | `modularize-ios` (같은 플러그인) |
| 주입 뒤 성능이 달라졌다 | 추측하지 않고 전후를 잰다 | `ios-measure:measure-ios` |

같은 플러그인 안은 이름 그대로, 다른 플러그인은 `플러그인:스킬` 형식이다.
**호출에 실패하면 원칙만 적용하고 계속 간다.**

## 0. 먼저 확인한다 — 사용자에게 묻는다

1. **왜 주입하나** — 이유마다 필요한 범위가 다르다

   | 이유 | 필요한 범위 |
   |---|---|
   | 테스트 대체물을 넣고 싶다 | 그 화면·타입 하나면 된다 (→ `test-seams` 가 더 맞다) |
   | 모듈 경계를 넘어야 한다 | 경계에 걸린 것만 |
   | 런타임에 구현을 갈아야 한다 (저장소 교체 등) | 그 인터페이스 하나 |
   | 전역 상태를 줄이고 싶다 | **전면. 여기가 가장 크다** |

2. **대상** — 싱글턴 하나인가, 여러 개인가
3. **범위** — 저장소 전체인가, 특정 모듈인가
4. **동작을 바꿔도 되는가** — 기본값은 **아니다.** 주입은 구조 변경이고 동작은 그대로여야 한다

---

## 1. 규모를 센다 (건너뛰지 않는다)

```sh
# 전체 규모
grep -rE '\.(shared|sharedInstance|default)\b' --include='*.swift' . | wc -l
grep -rlE '\.(shared|sharedInstance|default)\b' --include='*.swift' . | wc -l

# 타입별 참조 수 — 상위가 곧 난이도다
grep -rhoE '\b[A-Z][A-Za-z]*\.(shared|sharedInstance|default)\b' --include='*.swift' . \
    | sort | uniq -c | sort -rn | head -10

# 한 타입이 몇 파일에 퍼져 있나
grep -rl '<타입>.shared' --include='*.swift' . | wc -l
```

**전이 의존도 본다.** 싱글턴 A 를 주입으로 바꾸려는데 A 내부가 싱글턴 B 를 잡고 있으면
B 부터 해야 한다.

```sh
grep -nE '\.(shared|sharedInstance)\b' <대상 싱글턴 파일>
```

여기서 나온 숫자를 **2단계 전략표에 그대로 넣는다.** 감으로 전략을 고르지 않는다.

---

## 2. 규모에 맞는 전략을 고른다 — 전부 바꾸는 게 목표가 아니다

| 참조 수 | 전략 | 무엇을 하나 |
|---|---|---|
| **~20건** | **전면 전환** | 싱글턴을 없애고 전부 주입으로. 한두 커밋에 끝난다 |
| **~200건** | **잎부터** | 다른 것을 안 잡는 타입부터. 여러 커밋. 중간 상태가 생긴다 |
| **1,000건+** | **경계만** | **전환하지 않는다.** 새 코드와 모듈 경계에서만 주입받게 하고, 기존 호출부는 그대로 둔다 |

### 1,000건이면 왜 전환하지 않나

317개 파일을 고치는 변경은 **리뷰가 불가능하고 회귀 범위가 저장소 전체**다.
그리고 중간에 멈추면 두 방식이 섞인 채로 몇 달 간다. 얻는 것보다 잃는 것이 크다.

대신 **새로 만드는 코드가 싱글턴을 직접 잡지 못하게** 막는다.

```
기존 코드 ──▶ Singleton.shared         (그대로 둔다)
새 코드   ──▶ 주입받은 인터페이스 ──▶ 어댑터 ──▶ Singleton.shared
```

어댑터 하나가 싱글턴을 감싸고, 새 코드는 인터페이스만 안다.
**나중에 싱글턴을 없앨 때 고칠 곳이 어댑터 하나다.**

```swift
protocol SettingsStore { func value(for key: String) -> String? }

/// 레거시 싱글턴을 감싸는 어댑터. 새 코드는 이 프로토콜만 안다.
/// 싱글턴을 없앨 때 고칠 곳은 이 파일 하나다.
struct LegacySettingsStore: SettingsStore {
    func value(for key: String) -> String? { LegacySettings.shared.value(key) }
}
```

**이것을 "미완성" 으로 보고하지 않는다.** 규모를 재고 내린 결정이고, 기록에 그렇게 남긴다.

---

## 3. 조립 지점을 하나 만든다

**구현을 고르는 곳이 한 곳이어야** 주입의 값어치가 나온다.
여러 곳에서 각자 고르면 싱글턴과 다를 게 없다.

```swift
// 앱 진입부 한 곳에서만 등록한다
settingsStore = LegacySettingsStore()
itemClient    = LiveItemClient(baseURL: config.baseURL)
```

규칙 둘이다.

- **기본값을 주지 않는다.** `init(store: SettingsStore = LegacySettingsStore())` 로 두면
  주입을 잊은 호출부를 컴파일러가 잡아주지 못한다. 이주 중에는 이 유혹이 특히 강하다 —
  기본값을 주면 호출부를 안 고쳐도 컴파일되기 때문이다. **그게 이주가 멈추는 이유다**
- **조립 지점에 로직을 넣지 않는다.** 무엇을 고르는지만 있고 판단은 없어야 한다

---

## 4. 옮긴다 — 중간 상태를 견디게

**한 번에 다 못 바꾼다.** 싱글턴과 주입이 공존하는 기간이 반드시 있다.
그 기간을 견디게 만드는 것이 이 단계의 전부다.

| 규칙 | 왜 |
|---|---|
| **싱글턴을 지우지 않는다** (아직) | 남은 호출부가 컴파일 안 된다. 마지막에 지운다 |
| **잎부터 옮긴다** — 다른 싱글턴을 안 잡는 타입 | 전이 의존이 있으면 아래부터여야 한다 |
| **한 커밋 = 한 타입** | 회귀가 나면 어느 전환이 원인인지 갈린다 |
| **각 커밋이 스스로 빌드된다** | 중간 상태가 깨져 있으면 되돌릴 수 없다 |

전환 중에는 **같은 값을 두 경로로 읽는 자리**가 생긴다. 그게 가장 위험하다 —
한쪽에서 쓰고 다른 쪽에서 읽으면 값이 어긋난다.

```sh
# 같은 싱글턴을 직접 접근하면서 주입도 받는 타입 — 섞인 자리다
grep -rln 'SettingsStore' --include='*.swift' . \
    | xargs grep -ln 'LegacySettings.shared' 2>/dev/null
```

**섞인 자리가 나오면 그 타입은 한쪽으로 몰아야 한다.** 남겨 두지 않는다.

---

## 5. 남은 직접 접근을 센다

**"주입 구조로 바꿨다" 를 숫자로 말한다.**

```sh
# 1단계와 같은 명령으로 다시 센다
grep -rhoE '\b[A-Z][A-Za-z]*\.(shared|sharedInstance)\b' --include='*.swift' . \
    | sort | uniq -c | sort -rn | head -10
```

전후를 나란히 적는다.

```
              전      후
타입 C        22       0    전면 전환 완료
타입 B       178     171    잎 3개 전환
타입 A     1,284   1,284    의도적으로 유지 (경계 전략)
```

**줄지 않은 것에 이유를 적는다.** 숫자만 내고 이유가 없으면 미완성으로 읽힌다.

빌드는 사용자가 돌린다. **내가 돌리지 않았으면 돌리지 않았다고 적는다.**

## 6. 보고 형식

```
■ 규모 (실측)
   싱글턴별 참조 수 · 파일 수 · 전이 의존

■ 고른 전략과 근거
   전면 / 잎부터 / 경계만 — 규모 숫자와 함께

■ 조립 지점
   어디 한 곳인지. 기본값을 주지 않았는지

■ 전후 숫자
   싱글턴별 전 → 후. **줄지 않은 것에 이유**

■ 섞인 자리
   직접 접근과 주입을 동시에 하는 타입이 남았는지 (남으면 위험)

■ 의도적으로 남긴 것
   "미완성" 이 아니라 "결정" 이라는 것을 명시

■ 내가 돌리지 않은 것
   빌드·테스트를 돌렸는지
```

**"싱글턴을 걷어냈다" 를 쓰기 전에 5단계 숫자를 본다.**
줄지 않았는데 그렇게 쓰면, 다음 사람이 끝난 작업으로 알고 넘어간다.
