# 크래시 좁히기

**크래시는 추측으로 고치는 것이 가장 쉽고 가장 위험하다.** 증상을 가리는 수정
(`if` 하나 추가, 옵셔널 처리, `try?` 로 삼키기)은 크래시를 없애는 게 아니라
**다른 자리로 옮긴다.** 그리고 옮겨간 자리에서는 원인을 찾기가 더 어렵다.

이 절차의 순서가 중요하다. **신호로 원인군을 먼저 가른다.**
원인군이 갈리면 볼 곳이 절반 이하로 줄고, 안 갈리면 코드 전체를 의심하게 된다.

그리고 끝은 수정이 아니라 **6단계 — 크래시를 테스트로 박제하는 것**이다.
박제하지 않으면 같은 크래시가 다른 경로로 돌아온다.

---

## 어떻게 쓰나 — 실제 흐름

```
사용자: "화면을 나갔다 다시 들어오면 죽어"
   │
   ├─ 0단계  내가 4개를 묻는다 ──────────────▶ 사용자가 답한다
   │          (재현되나 · 로그 있나 · 빌드 구성 · 언제부터)
   │
   ├─ 1단계  신호로 원인군을 가른다
   │          SIGABRT / EXC_BAD_ACCESS / EXC_BREAKPOINT / watchdog
   │
   ├─ 2단계  스택에서 내 코드를 찾는다 (심볼화)
   │          프레임워크 프레임은 원인이 아니다
   │
   ├─ 3단계  가설을 하나로 좁혀 보고한다 ────▶ 사용자가 본다
   │          패턴 사전과 대조                    ■ 여기서 멈춘다
   │
   ├─ 4단계  재현 조건을 만든다
   │          못 만들면 못 만들었다고 적는다
   │
   ├─ 5단계  고친다 (증상이 아니라 원인)
   │
   ├─ 6단계  테스트로 박제한다 ───────────────▶ 사용자가 테스트 실행
   │          고치기 전에 실패하는 테스트부터        ■ 여기서 멈춘다
   │
   └─ 커밋 후보를 제시한다 ──────────────────▶ 사용자가 판단
```

**멈추는 지점이 셋이다.** 가설 보고 후(고치기 전), 테스트 박제, 커밋 전.

3단계에서 멈추는 이유가 이 스킬의 존재 이유다. **가설을 말하지 않고 고치기 시작하면
증상만 가려도 "고쳤다" 가 된다.** 무엇이 원인이라고 판단했는지 먼저 말한다.

### 기록은 파일로 남긴다 — 재개 지점

`.claude/crash/<증상>.md` 에 적는다. **추적되는 경로에 두지 않는다.** `.gitignore` 에 `.claude/` 가 있는지 먼저 확인한다
(`git check-ignore -q .claude/x && echo 무시됨`). 없으면 먼저 추가한다 — 없으면 작업 파일이 커밋 후보로 뜬다.

크래시 추적은 가설을 세우고 버리는 과정이고, 버린 가설을 잊으면 **같은 가설을 다시 세운다.**
간헐적 크래시는 며칠에 걸치기도 한다.

```markdown
## 증상
언제 / 어디서 / 빈도 / 언제부터

## 신호 (1단계)
EXC_BREAKPOINT (SIGTRAP) — Swift 런타임 트랩 계열

## 기각한 가설
- 이미지 로딩 경쟁 → 스택에 이미지 코드 없음. 버림
- 메모리 부족 → 로그에 압박 기록 없음. 버림

## 살아 있는 가설
- 서버가 같은 id 를 두 번 주면 사전 생성이 트랩 (패턴 A)

## 진행
- [x] 신호 분류
- [x] 심볼화
- [ ] 재현 조건 만들기   ← 여기서 멈췄다
- [ ] 테스트로 박제
```

**기각한 가설을 지우지 않는다.** 같은 가설을 다시 세우는 것을 막는 유일한 방법이다.

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| 원인이 취소되지 않는 브릿지다 | 취소 핸들러를 붙이고 취소를 실행해서 확인한다 | `async-migration` (같은 플러그인) |
| 크래시 지점에 테스트가 닿지 않는다 | 자리를 만들고 나서 박제한다 | `test-seams` (같은 플러그인) |
| watchdog 이고 메인 스레드 점유가 원인이다 | 추측하지 않고 점유 시간을 잰다 | `ios-measure:measure-ios` |
| 고치려면 구조를 옮겨야 한다 | 크래시 수정과 구조 변경을 같은 커밋에 섞지 않는다 | `legacy-port` (같은 플러그인) |

같은 플러그인 안은 이름 그대로, 다른 플러그인은 `플러그인:스킬` 형식이다.
**호출에 실패하면 원칙만 적용하고 계속 간다.**

---

## 0. 먼저 확인한다 — 사용자에게 묻는다

1. **재현되는가** — 손으로 재현되는 것과 리포트로만 오는 것은 완전히 다른 작업이다
2. **로그가 있는가** — 크래시 로그 / 리포팅 도구 / 콘솔 출력 중 무엇이 있는가
3. **빌드 구성** — Debug 인가 Release 인가. Release 는 최적화로 스택이 접혀 있을 수 있다
4. **언제부터인가** — 특정 버전부터면 그 사이 변경이 용의자다.
   `git log` 범위를 좁히는 것이 스택을 읽는 것보다 빠를 때가 있다

**리포트로만 오는 크래시는 4단계(재현)를 건너뛸 수밖에 없다.**
그때는 재현하지 못했다고 적고, 수정의 근거를 스택과 코드로만 세운다.

---

## 1. 신호로 원인군을 가른다

**로그에 적힌 예외 타입과 신호를 그대로 읽는다.** 추측으로 정하지 않는다.

| 신호 | 원인군 | 먼저 볼 것 |
|---|---|---|
| `EXC_BREAKPOINT (SIGTRAP)` | **Swift 런타임 트랩** — 강제 언래핑, 배열 범위, `precondition`, 정수 오버플로 | 스택 최상단의 내 코드 한 줄 |
| `SIGABRT` | ObjC 예외 · `assert` · 라이브러리가 던진 것 | 로그의 예외 이름과 reason 문자열 |
| `EXC_BAD_ACCESS (SIGSEGV/SIGBUS)` | **메모리** — 해제된 객체 접근, 스레드 경쟁 | 주소가 작은 값이면 nil 역참조 계열 |
| watchdog 종료 (`0x8badf00d`) | **메인 스레드 블로킹** | 메인 스레드 스택. 동기 I/O·큰 계산 |
| 메모리 부족 종료 | 크래시가 아니라 강제 종료 | 스택보다 메모리 사용 추이 |

**신호를 잘못 읽으면 절차 전체가 틀린다.** 로그가 없으면 신호도 모르는 것이고,
그때는 "신호 미확인" 으로 적고 2단계 대신 재현부터 시도한다.

크래시 로그 위치와 형식.

```sh
# 요즘 형식은 .ips (JSON 헤더 + 본문)
ls -t ~/Library/Logs/DiagnosticReports/*.ips | head -5

# 시뮬레이터 진단 수집
xcrun simctl diagnose
```

## 2. 스택에서 내 코드를 찾는다

**프레임워크 프레임은 원인이 아니다.** 최상단이 시스템 프레임이어도 원인은
그 아래 **내 코드 첫 프레임**에 있다.

```sh
# 심볼이 없는 주소를 함수로 바꾼다 (dSYM 필요)
atos -o <앱>.app.dSYM/Contents/Resources/DWARF/<앱> -arch arm64 -l <로드주소> <주소>

# 로그 전체를 심볼화
"$(xcode-select -p)"/../SharedFrameworks/DVTFoundation.framework/Versions/A/Resources/symbolicatecrash \
    <로그>.ips <앱>.app.dSYM
```

읽을 때 볼 것.

- **어느 스레드인가** — 메인인가 백그라운드인가. 이것만으로 원인군이 갈린다
- **내 코드 첫 프레임** — 여기가 출발점이다
- **같은 함수가 반복** — 재귀·순환 참조 해제 루프

---

## 3. 패턴 사전과 대조한다 — 가설을 하나로

아래는 **실제로 겪은 것들**이다. 증상이 맞으면 여기서 대개 끝난다.

| 패턴 | 증상 | 원인 | 확인 방법 |
|---|---|---|---|
| **A. 중복 키로 사전 생성** | 특정 계정·특정 데이터에서만 죽는다 | `Dictionary(uniqueKeysWithValues:)` 에 같은 키가 두 번. 서버가 중복을 주면 트랩 | 응답에서 키 중복 여부. **같은 값을 목록 식별자로도 쓰면 두 곳에서 죽는다** |
| **B. 없는 섹션·항목 조회** | 화면을 나갔다 다시 들어오면 죽는다 | 스냅샷·데이터소스에 그 섹션이 있는지 확인하지 않고 물었다 | 조회 전에 존재 확인이 있는지 |
| **C. continuation 미재개** | 대기 중 화면을 나가면 죽는다 | 취소를 인지하지 못하는 브릿지. 재개되지 않은 채 작업이 해제됨 | `withCheckedThrowingContinuation` 수와 `withTaskCancellationHandler` 수의 차이 |
| **D. `deinit` 에서 격리 상태 접근** | 해제 시점에 죽는다 | `deinit` 에서 액터 격리 프로퍼티를 만졌다 | `deinit` 안의 프로퍼티 접근 |
| **E. 스레드 경쟁** | 간헐적. 재현이 안 된다 | 같은 컨테이너를 두 스레드에서 쓴다 | **Thread Sanitizer** (아래) |
| **F. 재사용 셀의 직전 상태** | 스크롤하다 죽거나 잘못 보인다 | 셀을 재사용할 때 이전 상태를 지우지 않았다 | `prepareForReuse` 와 구성 함수 |
| **G. 참조 순환으로 해제 안 됨** | 죽지는 않는데 메모리가 안 줄고 나중에 터진다 | 클로저가 `self` 를 강하게 잡았다. **인자를 무시한 클로저가 흔한 원인** | 클로저 캡처 목록 |

**A·B 는 테스트로 박제할 수 있다.** 입력만 만들면 재현되므로 6단계에서 반드시 박제한다.
**E 는 도구가 필요하다.**

### 재현이 안 되면 도구로 좁힌다

```sh
# 스레드 경쟁 (패턴 E)
xcodebuild test ... -enableThreadSanitizer YES

# 메모리 오류 (해제된 객체 접근)
xcodebuild test ... -enableAddressSanitizer YES

# 정의되지 않은 동작 (오버플로 등)
xcodebuild test ... -enableUndefinedBehaviorSanitizer YES
```

세 플래그 모두 `xcodebuild -help` 에 실재하는 것을 확인했다. **인자가 필요하다** (`YES`).
새니타이저는 느려지므로 대상 테스트만 좁혀서 돌린다.

**여기서 가설을 하나로 정해 보고하고 멈춘다.** 두 개 이상이면 어느 쪽인지 가리는
방법을 함께 적는다.

## 4. 재현 조건을 만든다

**재현되면 수정의 근거가 생기고, 안 되면 근거가 스택뿐이다.** 그 차이를 보고에 적는다.

간헐적 크래시를 재현하는 방향.

| 조건 | 왜 |
|---|---|
| 같은 동작을 빠르게 반복 | 경쟁·중복 요청 계열이 드러난다 |
| 대기 중에 이탈 | 취소·continuation 계열 (패턴 C) |
| 응답을 느리게 만든다 | 대기 창을 넓혀야 이탈 타이밍을 잡을 수 있다 |
| 데이터를 비정상으로 만든다 | 중복 키·빈 배열 (패턴 A·B) |
| 화면을 여러 번 들락날락 | 해제 시점 (패턴 D·G) |

**응답이 빠르면 취소 창이 안 열린다.** 취소 계열(패턴 C)의 재현 조건과 실패 사례는
`async-migration` 4단계에 있다. 여기서는 재현하지 못했으면 못 했다고 적는 것까지만 한다.

---

## 5. 고친다 — 증상이 아니라 원인

**아래는 증상 가리기다. 원인을 못 찾았을 때 하는 짓이다.**

| 하지 말 것 | 왜 |
|---|---|
| `if` 하나 추가해서 그 경로를 막는다 | 왜 그 값이 들어왔는지 모른 채 막는다 |
| `try?` 로 에러를 삼킨다 | 실패가 조용해져서 다음에 더 늦게 발견된다 |
| 값을 하드코딩한다 | 다른 입력에서 같은 크래시가 난다 |
| 옵셔널로 바꿔 언래핑을 피한다 | nil 이 들어오는 원인이 그대로 남는다 |

**원인을 고치는 방향은 계약을 바꾸는 것이다.**

```
중복 키가 온다     → 중복을 허용하는 자료구조로 바꾸거나, 들어오는 자리에서 합친다
없는 섹션을 묻는다  → 묻기 전에 존재를 확인하거나, 존재를 타입으로 강제한다
취소를 모른다      → 취소를 전달한다 (막지 않고)
```

**타입으로 막을 수 있으면 런타임 검사보다 낫다.** 컴파일이 잡아주면 다음 사람이 못 어긴다.

---

## 6. 테스트로 박제한다 — 이 단계가 끝이다

**고치기 전에 실패하는 테스트를 먼저 쓴다.** 순서를 바꾸면 그 테스트가 정말 이 크래시를
잡는지 알 수 없다.

```
1. 크래시를 재현하는 테스트를 쓴다 → 빨간 것을 확인한다
2. 고친다 → 초록이 되는 것을 확인한다
3. 고친 것을 되돌려 본다 → 다시 빨개지는지 확인한다
```

3번을 건너뛰지 않는다. 테스트가 다른 이유로 초록이 됐을 수 있다.

박제하기 쉬운 것과 어려운 것을 구분한다.

| 박제 | 대상 |
|---|---|
| 쉽다 | 중복 키 · 빈 배열 · 없는 섹션 · 경계값 (입력만 만들면 된다) |
| 중간 | 취소 · 재시도 (시점을 제어할 자리가 필요하다) |
| 어렵다 | 스레드 경쟁 (새니타이저를 CI 에 넣는 것이 현실적) |

**어려운 것을 박제하지 못했으면 그렇게 적는다.** 박제한 척하지 않는다.

## 7. 보고 형식

```
■ 증상과 신호
   언제 죽는지 / 신호 (없으면 "신호 미확인")

■ 기각한 가설
   무엇을 왜 버렸는지 ← 이것을 적는 것이 다음 사람에게 가장 값어치 있다

■ 원인
   패턴 사전의 어느 것인지, 또는 새 패턴인지
```

**"고쳤다" 를 쓰기 전에 확인한다.** 재현하지 못한 크래시를 고쳤다고 쓰면,
다음에 같은 크래시가 왔을 때 이 기록이 사람을 잘못된 방향으로 보낸다.
재현 못 했으면 **"스택과 코드로 판단한 수정"** 이라고 적는다.
