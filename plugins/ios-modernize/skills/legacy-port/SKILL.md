# 레거시 포팅

**리팩토링은 동작을 바꾸지 않는다.** 하나라도 달라지면 그건 리팩토링이 아니라 기능 변경이고,
그렇게 보고해야 한다.

이 절차의 핵심은 4단계가 아니라 **1단계다.** 옮기기 전에 현재 동작을 적어두지 않으면
"동작을 보존했다" 는 주장 자체가 불가능하다. 나중에 기억으로 대조하면 반드시 빠뜨린다.

---

## 어떻게 쓰나 — 실제 흐름

```
사용자: "설정 화면 새 구조로 옮겨줘"
   │
   ├─ 0단계  내가 4개를 묻는다 ─────────────▶ 사용자가 답한다
   │          (대상 · 레퍼런스 · 개선 허용 · 옮기지 않을 것)
   │
   ├─ 1단계  기준선 파일을 만들어 보여준다 ──▶ 사용자가 훑는다
   │          .claude/baseline/<대상>.md          "이것도 있어" / "그건 아니야"
   │          ※ 여기서 승인을 받고 넘어간다
   │
   ├─ 2·3단계 사용처 전수 + 신규 패턴 조사 ──▶ 결과를 보고
   │          모호하면 여기서 묻는다
   │
   ├─ 4단계  옮긴다 (아래 계층부터)
   │
   ├─ 5단계  기준선과 대조한 표를 낸다 ──────▶ 사용자가 빌드·실행
   │          달라진 항목만 설명                  실제 화면을 확인
   │
   └─ 커밋 후보를 제시한다 ─────────────────▶ 사용자가 커밋 여부 판단
```

**멈추는 지점이 두 곳이다.** 1단계 승인 전, 그리고 커밋 전. 나머지는 이어서 간다.

### 기준선 파일은 어디 두나

`.claude/baseline/<대상>.md`. **추적되는 경로에 두지 않는다** — 작업 산출물이 커밋 후보로
섞이면 안 된다. 저장소에 남겨야 할 이유가 생기면 그때 커밋 후보가 몇 개 늘어나는지 함께 말한다.

### 작업이 길어져 대화가 끊기면

포팅은 한 번에 안 끝난다. 대화가 요약되거나 세션이 바뀌면 **기준선 파일이 재개 지점이다.**
그래서 기록을 머리에 두지 않고 파일로 남긴다. 재개할 때는 그 파일을 먼저 읽는다.

진행 상태를 파일 안에 표시해 둔다.

```markdown
## 진행
- [x] 기준선 기록 (사용자 승인 2026-08-18)
- [x] 사용처 3곳 확인
- [ ] 데이터 계층 이동   ← 여기서 멈췄다
- [ ] 화면 이동
- [ ] 대조
```

### 다른 절차로 넘기는 지점

**아래는 지켜야 할 원칙이고, 같은 이름의 스킬은 그 원칙을 절차로 풀어놓은 것이다.**
스킬이 설치돼 있으면 `Skill` 로 부르고, **없으면 원칙만 지키고 그대로 진행한다.**
없는 스킬을 부르려고 멈추지 않는다.

| 이런 게 나오면 | 지킬 원칙 | 절차가 있는 스킬 |
|---|---|---|
| 테스트가 닿을 자리가 없다 | 자리를 먼저 만들고 테스트를 붙인다. 안 닿는 곳에 테스트를 붙여 초록으로 만들지 않는다 | `test-seams` (같은 플러그인) |
| 느려졌다 / 원래 느렸다 | **추측으로 고치지 않는다.** 재고 나서 고친다 | `measure-ios` (`ios-measure` 플러그인) |
| 경계를 세워야 옮길 수 있다 | 공유물을 아래 계층으로 내린다. 위반이 컴파일되지 않는지 확인한다 | `modularize-ios` (같은 플러그인) |
| 콜백·Rx → async 가 본론이다 | 취소 전파와 continuation 재개를 먼저 확인한다 | `async-migration` (같은 플러그인) |

**이름으로 부를 때 주의.** 같은 플러그인 안의 스킬은 이름 그대로(`test-seams`),
다른 플러그인의 스킬은 `플러그인:스킬`(`ios-measure:measure-ios`) 형식이다.
어느 쪽이든 **호출에 실패하면 원칙만 적용하고 계속 간다** — 포팅이 도구 때문에 멈추면 안 된다.

**포팅과 성능 개선을 같은 작업으로 섞지 않는다.** 둘을 섞으면 느려진 원인이
포팅인지 원래 그랬는지 갈리지 않는다.

### 커밋은 어떻게 쪼개나

```
1. refactor: <대상>을 <신규 패턴>으로 옮긴다      ← 동작 변화 0
2. fix: <레거시에 있던 버그>를 고친다              ← 5단계에서 찾은 것
3. test: <옮긴 로직>에 회귀 테스트를 붙인다
```

**1번에 2번을 섞지 않는다.** 섞으면 나중에 회귀가 났을 때 어느 쪽이 원인인지 못 가린다.
커밋은 사용자가 지시할 때만 한다. **빌드는 사용자가 직접 돌린다.**

---

## 0. 먼저 확인한다 — 사용자에게 묻는다

추측으로 시작하면 절반쯤 가서 되돌린다.

1. **무엇을 옮기는가** — 화면 하나인가, 흐름 전체인가, 데이터 계층만인가
2. **신규 패턴의 레퍼런스는 무엇인가** — 이 저장소에서 "가장 최근에 제대로 만든" 모듈.
   그 구조를 템플릿으로 쓴다
3. **동작을 개선해도 되는가** — 기본값은 **아니다**. UI/UX 만 개선하고 로직은 그대로 두는 것이
   대부분의 포팅 요구다. 개선 범위가 있으면 지금 못 박는다
4. **옮기지 않는 것** — 스코프를 여기서 고정한다. 작업 중 발견한 기존 문제는 이 목록에 넣고
   건드리지 않는다

---

## 1. 기준선을 기록한다 (건너뛰지 않는다)

**코드를 한 줄도 고치기 전에** 현재 동작을 파일로 적는다. 추적되지 않는 경로에 둔다.

읽어서 적는 것과 실행해서 확인한 것을 **구분해서** 표시한다.

```markdown
# <대상> 기준선  (옮기기 전)

## 진입 경로
- 어디서 어떻게 들어오는가 / 파라미터로 무엇이 넘어오는가

## 화면에 나오는 상태
| 상황 | 지금 무엇이 보이는가 | 확인 |
|---|---|---|
| 로딩 중 | | 실행 |
| 성공 | | 실행 |
| 빈 결과 | | 코드 |
| 서버 4xx | | 코드 |
| 서버 5xx | | 코드 |
| 네트워크 없음 | | 미확인 |

## 분기 조건 (원문 그대로 옮긴다)
- `if flag == false` → ... (조건이 뒤집혀 보여도 지금은 그대로 적는다)

## 호출 순서와 타이밍
1. viewDidLoad → A 호출
2. A 응답 → B 호출          ← 순차인지 병렬인지 적는다
3. 화면 갱신 몇 번 일어나는가

## 에러 처리
- 어떤 에러가 어떤 문구로 나오는가 (문구는 키가 아니라 **실제 표시 문자열**)
- 삼켜지는 에러가 있는가

## 취소·이탈
- 응답 대기 중 화면을 나가면 무엇이 취소되는가 / 취소되지 않는가

## 문자열
- 하드코딩 문자열 목록 / 로컬라이즈 키 목록
```

**분기가 이상해 보여도 지금 고치지 않는다.** 기준선은 "옳은 동작" 이 아니라 "현재 동작" 의 기록이다.
고칠 것은 5단계에서 별건으로 다룬다.

---

## 2. 영향 범위를 센다

옮기는 대상이 **공유 코드**면 포팅이 회귀를 만든다. 먼저 사용처를 전수로 센다.

```sh
# 타입·함수 이름으로 전체 검색. 정의 외에 몇 곳에서 나오는지
grep -rn "TypeName" --include='*.swift' . | grep -v 'TypeName.swift'
```

셀 때는 **검색 범위를 함께 말한다.** "여기뿐" 이 아니라 "타입명으로 검색한 결과 3곳".

사용처가 여러 곳이면 옮기는 것이 아니라 **새로 만들고 기존을 남기는** 선택지도 검토한다.
어느 쪽인지 사용자에게 확인받는다.

---

## 3. 신규 패턴을 코드베이스에서 찾는다

**임의로 짜지 않는다.** 같은 일을 하는 기존 구현을 먼저 찾아 그 패턴을 따른다.

찾을 것:

- 같은 계층의 형제 디렉토리에 같은 역할의 파일이 있는가
- 공통 모듈에 이미 있는 컴포넌트를 새로 만들려 하고 있지 않은가
- 이 저장소는 상태를 어떻게 담는가 / 네비게이션을 누가 하는가 / 에러를 어떻게 표시하는가
- 테스트는 어느 계층에 붙어 있는가

```sh
ls <대상의 부모 디렉토리>          # 형제 모듈을 먼저 본다
grep -rn "<하려는 것과 같은 일>" --include='*.swift' <공통 모듈 경로>
```

**SDK·프레임워크의 이름을 추측하지 않는다.** `grep` / `Read` 로 실재를 확인한 뒤 쓴다.

---

## 4. 옮긴다 — 아래 계층부터

위에서 시작하면 아래가 흔들릴 때마다 다시 그린다.

```
모델 → 데이터 접근 → 로직 → 화면
```

규칙:

- **데이터 계층에 UI 의존성을 넣지 않는다.** 화면 전환·알럿·뷰 타입이 데이터 계층에 들어가면
  레거시를 그대로 옮긴 것이라도 잘못 옮긴 것이다
- **로컬라이즈 문자열을 `static let` 에 캐시하지 않는다.** 첫 평가 시점의 언어가 영구히 남는다.
  computed property 나 함수로 둔다
- **catch-all(Repository / UseCase / Service)을 쪼갤 때 이름·범위가 모호하면 묻는다.**
  혼자 정하고 넘어가지 않는다
- 순수 로직(계산·판정·포맷)은 화면 밖으로 빼서 테스트를 붙인다. 그것만으로도 회귀 그물이 생긴다

---

## 5. 기준선과 대조한다 — 항목마다 O/X

1단계의 기록을 열고 **한 줄씩** 확인한다. "괜찮아 보인다" 는 확인이 아니다.

| 항목 | 어떻게 확인하나 |
|---|---|
| **분기** | 조건식을 나란히 놓고 읽는다. 부정·순서·기본값이 같은지 |
| **호출 순서** | 순차였던 것이 병렬이 되지 않았는지. 병렬은 취소 동작을 바꾼다 |
| **타이밍** | 화면 갱신 횟수가 같은지. 1번이 2번이 되면 깜빡임이 생긴다 |
| **에러 처리** | 같은 실패에 같은 문구가 나오는지. 삼켜졌던 에러를 갑자기 노출하지 않는지 |
| **표시 문자열** | 키가 아니라 **화면에 뜨는 문자열**을 비교한다 |
| **취소·이탈** | 대기 중 이탈했을 때 동작이 같은지 |
| **스레드** | 메인에서 하던 것을 백그라운드로 옮기지 않았는지 (그 반대도) |

**하나라도 달라졌으면 그것은 기능 변경이다.** 되돌리거나, 의도한 변경이라고 보고한다.
"어차피 이게 맞는 동작이니까" 로 조용히 넘기지 않는다 — 그 판단은 사용자 몫이다.

### 기준선이 틀렸다고 판단되면

레거시 동작 자체가 버그일 때가 있다 (조건 뒤집힘, 삼켜진 에러).
**포팅 커밋에 섞지 않는다.** 별 커밋으로 분리하고 메시지에 왜 바꿨는지 적는다.
그러면 나중에 회귀를 추적할 수 있다.

---

## 6. 개선과 레거시가 충돌하면

새 구조에서 의도적으로 개선한 것(모달 → push, 즉시 로딩 표시 등)이 레거시 동작과 부딪히면
**되돌리기가 기본값이 아니다.** 개선을 유지한 채 근본 원인을 고친다.

되돌릴지는 사용자에게 묻는다. 묻지 않고 되돌리면 개선이 조용히 사라진다.

---

## 7. 보고 형식

```
■ 옮긴 것
   대상 / 어느 패턴을 레퍼런스로 삼았는지

■ 기준선 대조 결과
   분기 O / 순서 O / 타이밍 O / 에러 O / 문자열 O / 취소 X ← 달라진 것만 설명
   (확인 방법을 함께: 읽어서 확인 / 실행해서 확인 / 미확인)

■ 동작이 달라진 것 (있으면)
   무엇이 어떻게 / 의도한 것인지 / 되돌릴지 판단 요청

■ 옮기지 않은 것
   0단계에서 고정한 스코프 밖 항목

■ 물어야 할 것
   이름·범위가 모호해서 임의로 정하지 않은 지점
```

**빌드·테스트를 돌리지 않았으면 돌리지 않았다고 적는다.** 통과했다고 쓰지 않는다.
