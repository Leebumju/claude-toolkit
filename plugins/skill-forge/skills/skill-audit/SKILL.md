# 스킬 점검

스킬을 만든 직후에는 무엇이 빠졌는지 보이지 않는다. 방금 쓴 사람에게는 전부 자명하기 때문이다.
**분량이 늘면 완성된 것처럼 느껴지는데, 분량과 실효는 무관하다.**

이 절차는 **고치지 않는다.** 빠진 것을 목록으로 낸다.
고칠지는 사람이 정한다.

---

## 어떻게 쓰나

```
사용자: "legacy-port 스킬 뭐가 부족해?"
   │
   ├─ 1단계  기계 검사 ──────── 프론트매터·링크·명령어 실재
   ├─ 2단계  구조 검사 ──────── 흐름·멈추는 지점·폴백
   ├─ 3단계  실효 검사 ──────── 지시가 행동을 바꾸는지
   ├─ 4단계  냄새 검사 ──────── 지식 문서화·분량 부풀리기
   └─ 보고 (심각도순)  ─────────▶ 사람이 고칠 것을 고른다
```

한 번에 여러 스킬을 볼 때도 **한 스킬씩** 끝낸다. 섞으면 어느 스킬의 문제인지 흐려진다.

1단계는 동봉한 스크립트가 대신한다.

```sh
./audit.sh <스킬 루트 또는 SKILL.md>
```

### 결과를 파일로 남긴다 — 재개 지점

스킬이 여러 개면 점검과 수정이 한 번에 안 끝난다. 결과를 `.claude/skill-audit.md` 에 적는다.
**추적되는 경로에 두지 않는다.** **파일을 만든 뒤 그 파일이 실제로 안 뜨는지 확인한다.**

```sh
git status --porcelain <내가 만든 파일>   # 아무것도 안 나와야 한다
```

`git check-ignore` 만으로는 부족하다. 이유가 둘이다.

**하나 — 디렉토리로 물으면 답이 거꾸로 나온다.** 실측하면 이렇다.

```
git check-ignore -v .claude          → rc=1  (무시 안 됨으로 보인다)
git check-ignore -v .claude/x/y.md   → rc=0  (.gitignore 규칙을 짚는다)
```

디렉토리 자체는 무시 대상으로 보고되지 않는다. **파일로 물어야 규칙이 나온다.**

**둘 — `.gitignore` 에 있어도 이미 추적 중인 파일은 계속 추적된다.**
실제 저장소에서 `.claude/` 가 무시 대상인데 그 안에 추적 중인 파일이 10개 있었다.

그래서 **내가 만든 파일을 `git status --porcelain` 으로 직접 묻는다.** 그게 유일한 확답이다 — 없으면 작업 파일이 커밋 후보로 뜬다.

기억으로 이어가면 "이건 오탐이라 넘기기로 했다" 를 잊고 같은 항목을 다시 신고한다.

```markdown
## <스킬 이름>
- [x] description 트리거 없음 → 4개 추가
- [ ] 무력한 문장 3건       ← 여기서 멈췄다
- [~] 읽기 전용 경고        → **오탐**. "추측으로 고치지 않는다" 를 잡은 것. 검사 쪽을 고쳤다
```

**오탐은 지우지 않고 오탐이라고 표시한다.** 검사 자체를 고칠 근거가 된다.

### 검사가 틀렸을 때

이 절차를 돌리면 **검사 자체의 결함이 먼저 나온다.** 실제로 한 번에 네 건이 나왔다 —
인용을 지시로 오판, 단계 표기 형식 누락, 동봉 파일과 대상 프로젝트 파일 혼동, 읽기 전용 패턴 과탐.

**대상 스킬을 고치기 전에 검사를 고친다.** 순서를 바꾸면 오탐에 맞춰 멀쩡한 스킬을 망친다.

## 1. 기계 검사 — 확정적으로 틀린 것

여기서 나오는 것은 논쟁 대상이 아니다. 전부 감점이다.

```sh
F=<SKILL.md 경로>

# 프론트매터 필수 항목
head -20 "$F" | grep -E '^(name|description|allowed-tools|argument-hint):'

# name 이 디렉토리 이름과 같은가 (다르면 호출이 안 잡힌다)
basename "$(dirname "$F")"; grep -m1 '^name:' "$F"

# 문서가 참조하는 파일이 실재하는가
grep -oE '`[^`]+\.(sh|md|swift|json|yml)`' "$F" | tr -d '`' | sort -u

# 코드블록 언어 표시가 있는가 (없으면 렌더가 깨진다)
grep -c '^```$' "$F"
```

| 검사 | 실패 조건 |
|---|---|
| `name` | 없음, 또는 디렉토리 이름과 불일치 |
| `description` | 없음, 또는 **부르는 말이 안 들어 있음** (아래 참조) |
| `allowed-tools` | 파일을 고치는 절차인데 `Edit`/`Write` 가 없음. 읽기 전용이라 주장하면서 `Edit` 가 있음 |
| 참조 파일 | 문서가 가리키는 스크립트·템플릿이 저장소에 없음 |
| 명령어 | `--flag` 가 그 도구에 실재하는지 확인 안 됨 |

### `description` 은 색인이다

스킬은 사람이 이름을 외워서 부르는 게 아니라 **`description` 이 대화와 맞아서** 뜬다.
그래서 여기에 **사용자가 실제로 쓸 말**이 들어 있어야 한다.

```
약함   "iOS 앱의 성능을 개선하는 절차"
강함   "...\"느리다\", \"왜 이렇게 오래 걸리지\", \"이거 재봐\" 에 답한다"
```

**언제 쓰지 않는지도** 적혀 있으면 더 좋다. 비슷한 스킬이 둘 있으면 서로를 밀어낸다.

## 2. 구조 검사 — 절차로 성립하는가

| 항목 | 없으면 무슨 일이 나나 |
|---|---|
| **실행 흐름** (누가 언제 무엇을) | 부를 때마다 순서가 달라진다 |
| **멈추는 지점** | 승인 없이 끝까지 달려서, 전제가 틀렸는데 다 해버린다 |
| **첫 단계에서 묻는 것** | 추측으로 시작해 절반쯤 가서 되돌린다 |
| **산출물 위치** | 작업 파일이 저장소에 섞여 커밋 후보가 된다 |
| **재개 지점** | 대화가 끊기면 기억으로 이어가서 앞 결론이 흐려진다 |
| **다른 스킬로 넘기는 조건** | 한 스킬이 모든 걸 하려 든다 |
| **폴백** | 참조한 스킬이 없으면 절차가 멈춘다 |
| **보고 형식** | 결과가 매번 다른 모양으로 나온다 |

### 특히 볼 것 — 참조가 살아 있는가

다른 스킬을 가리키면 **그게 실재하는지** 확인한다.

```sh
# 문서가 가리키는 스킬 이름을 뽑아 실재 확인
grep -oE '`[a-z][a-z0-9-]+`' "$F" | tr -d '`' | sort -u
find <스킬 루트> -name SKILL.md -exec grep -l '^name: <이름>' {} \;
```

없는 스킬을 가리키면 **폴백이 명시돼 있어야** 통과다. "없으면 원칙만 지키고 계속 간다" 같은 문장.
폴백 없이 없는 스킬을 가리키는 것은 절차가 끊긴 것이다.

**플러그인이 다르면 이름 형식이 다르다.** 같은 플러그인 안은 이름 그대로,
다른 플러그인은 `플러그인:스킬`. 형식이 틀리면 호출이 안 잡힌다.

## 3. 실효 검사 — 이 문장이 행동을 바꾸는가

가장 중요한 단계다. **한 절씩 읽고 이 질문을 한다.**

> 이 문장이 없을 때와 있을 때, 내가 다르게 행동하는가?

### 이 단계는 쓴 사람이 할 수 없다

**방금 쓴 사람에게는 모든 문장이 자명하다.** 그래서 위 질문이 성립하지 않는다.
"꼼꼼히 확인한다" 를 쓴 사람은 자기가 무엇을 확인할지 알고 있으므로 그 문장이 충분해 보인다.

그래서 3·4단계는 **그 스킬을 쓰지 않은 쪽에 넘긴다.**

- 이 대화를 물려받지 않는 **별도 세션**에 넘긴다
- **읽기 전용**으로 넘긴다. 고칠 수 있으면 "고쳤으니 통과" 로 끝난다
- **렌즈를 하나로 좁힌다.** 실효성과 냄새를 한 번에 주면 아무것도 깊게 보지 않는다

**`grep` 으로 흉내 내지 않는다.** 무력한 문장의 특징은 단어가 아니라 **확인 방법의 부재**라서,
같은 줄만 보는 검사는 바로 아래에 판정표가 있는 강한 문장을 오탐한다.
실제로 그렇게 오탐이 났다 — 판정 근거가 다음 줄에 있는 문장을 무력하다고 신고했다.

1·2단계까지만 돌리고 3·4단계를 건너뛰었으면 **보고서에 그렇게 적는다.**
"검사받았다" 와 "기계 검사만 받았다" 는 다른 말이다.

바꾸지 않는 문장의 전형이다.

| 무력한 문장 | 왜 무력한가 | 대신 |
|---|---|---|
| "꼼꼼히 확인한다" | 확인 방법이 없다 | "`grep -c` 결과와 문서 수치를 나란히 출력한다" |
| "적절한 이름을 쓴다" | 판정 기준이 없다 | "역할이 이름에서 보이는지. 안 보이면 묻는다" |
| "테스트를 작성한다" | 무엇을 고를지가 빠졌다 | "실패 경로 · 재시도 · 취소 · 중복 요청 네 개를 먼저" |
| "성능을 고려한다" | 측정이 없다 | "16.7ms 를 넘는지 잰다" |

### 검사 가능한 지시인지 본다

각 단계에 **확인 방법**이 붙어 있는가. "이러면 안 된다" 만 있고
"이렇게 확인한다" 가 없으면 지켜지지 않는다.

```
약함   경계를 지켜야 한다
강함   위반 import 를 넣어 빌드가 죽는지 본다. 안 죽으면 주장은 거짓이다
```

### 실패 사례가 있는가

"실제로 이렇게 물렸다" 가 한 줄이라도 있으면 규칙이 산다.
근거 없는 규칙은 바쁠 때 가장 먼저 버려진다.

## 4. 냄새 검사 — 있으면 의심한다

| 냄새 | 판정 |
|---|---|
| **지식을 설명한다** (프레임워크·패턴 소개) | 스킬이 아니라 문서다. 절차가 없으면 잘라낸다 |
| **한 절이 유독 크다** | 그 절이 **조회표**(명령 목록)면 참조 파일로 뺀다. 절차·근거면 그대로 둔다 |
| **단계가 8개를 넘는다** | 실제로는 끝까지 안 읽힌다 |
| **"상황에 따라 판단한다"** | 판단 기준을 안 정한 것이다 |
| **예시가 전부 가상** | 실제 명령·실제 출력이 없으면 검증되지 않은 절차다 |
| **차단한다** (실패 시 진행 불가) | 마감 직전에 사람이 도구를 끈다. 보고하고 진행하게 둔다 |
| **회사·프로젝트 고유 정보** | 공개 저장소면 유출이고, 아니어도 재사용이 막힌다 |
| **"완벽하게", "반드시 모두"** | 검증 불가한 강한 주장 |

**줄 수로 판정하지 않는다.** 기준을 세 번 바꿔 봤고 전부 오탐이 났다 —
`300줄 초과`(실측 근거가 붙으면 400줄이 정상이다), `최대 절 25% 초과`(절이 적은
스킬은 한 절이 자연히 크다), `평균의 3배`(흐름도가 걸린다).

**코드 비중으로도 안 갈린다.** 계측 코드 본문이 49%, 진행 템플릿이 70%인데
둘 다 빼면 안 되는 것이다.

**어디가 큰지는 기계가 보여주고, 조회표인지는 사람이 판정한다.**
`audit.sh` 는 400줄을 넘는 스킬의 상위 절 셋을 출력만 하고 판정하지 않는다.

### 겹침 검사

다른 스킬과 **부르는 말이 겹치면** 둘 다 안 뜨거나 엉뚱한 쪽이 뜬다.

```sh
grep -h '^description:' $(find <스킬 루트> -name SKILL.md) | tr ',' '\n' | grep -oE '"[^"]+"' | sort | uniq -c | sort -rn | head
```

같은 트리거 문구가 두 스킬에 있으면 **한쪽에서 빼거나 "이럴 때는 저쪽" 을 적는다.**

## 보고 형식

```
■ 대상
   스킬 이름 / 줄 수 / 단계 수

■ 확정 결함 (기계 검사)
   파일:줄 — 무엇이 틀렸는지

■ 빠진 구조
   흐름 / 멈추는 지점 / 폴백 / 재개 지점 / 보고 형식 중 없는 것

■ 무력한 문장 (줄 번호와 함께)
   원문 인용 → 왜 행동을 바꾸지 못하는지 → 대신 무엇을 쓸지

■ 냄새
   해당 항목과 근거

■ 다른 스킬과 겹치는 트리거
   겹치는 문구 / 어느 쪽이 이겨야 하는지

■ 통과한 항목
   (마지막에 짧게)

■ 내가 확인하지 않은 것
   실행해 보지 않은 명령, 열어 보지 않은 참조
```

**일반론을 쓰지 않는다.** `파일:줄` 로 짚고 원문을 인용한다.
"개선하면 좋겠습니다" 로 완충하지 않는다. 빠진 것은 빠졌다고 쓴다.

고치지 않는다. **읽기 전용이다.**
